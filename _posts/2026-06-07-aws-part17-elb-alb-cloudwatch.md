수많은 EC2 서버로 들어오는 트래픽을 효율적으로 분산시켜 주는 **Elastic Load Balancer(ELB)**,  
그중에서도 Application Load Balancer(ALB)의 구조·요금·리스너 규칙과  
**CloudWatch를 활용한 모니터링**까지 정리합니다.

---

## ELB (Elastic Load Balancer) 개요

둘 이상의 가용 영역(AZ)에 있는 여러 대상(EC2, 컨테이너, IP 등)으로 수신 트래픽을 자동으로 분산시켜 주는 서비스입니다.

> **비유:** 공항 체크인 카운터 배분 시스템입니다.  
> 승객(트래픽)이 공항에 들어오면, ELB가 "5번 카운터로 가세요"라고 안내합니다.  
> 덕분에 특정 카운터만 줄이 길어지는 일 없이 모든 카운터(EC2)가 고르게 처리합니다.  
> 카운터 직원이 자리를 비우면(Health Check 실패), ELB는 그쪽으로 더 이상 승객을 보내지 않습니다.

### 주요 특징

- **상태 확인 (Health Check):** 직접 트래픽을 발생시켜 연결된 서버들이 살아있는지 지속적으로 체크합니다. 죽은 서버가 있다면 그쪽으로는 트래픽을 보내지 않습니다.
- **IP 고정 불가:** ELB 자체의 IP 주소는 내부적으로 지속해서 변동되므로, **항상 제공되는 도메인(DNS)으로 접속**해야 합니다. (NLB 예외)

---

## ELB의 4가지 종류

| 종류 | 계층 | 특징 |
|---|---|---|
| **ALB** (Application Load Balancer) | L7 | HTTP/HTTPS 기반, 요청 내용을 보고 세밀한 라우팅 가능 |
| **NLB** (Network Load Balancer) | L4 | TCP/UDP 기반, 초저지연, **유일하게 고정 IP(Elastic IP) 할당 가능** |
| **CLB** (Classic Load Balancer) | L4/L7 | 구형 타입, 현재 사용 비권장 |
| **GWLB** (Gateway Load Balancer) | L3 | 방화벽 등 가상 어플라이언스 배포·관리용 |

> **비유 (ALB vs NLB):**  
> ALB는 여권과 목적지를 확인하는 안내 직원입니다. 국내선인지 국제선인지, 비즈니스석인지 이코노미석인지 보고 알맞은 카운터로 안내합니다.  
> NLB는 자동 체크인 키오스크입니다. 내용은 깊이 보지 않지만, 무조건 빠르게 처리합니다.  
> 정교한 라우팅이 필요하면 ALB, 초저지연 처리가 필요하면 NLB입니다.

## ALB의 핵심 구성 요소

### 대상 그룹 (Target Group)

트래픽을 최종적으로 전달받을 목적지(서버들)의 논리적인 집합입니다.

| 대상 유형 | 설명 |
|---|---|
| EC2 인스턴스 | 일반적인 웹 서버 |
| 고정 IP | 온프레미스 서버 등 |
| Lambda 함수 | 서버리스 함수 |
| 다른 ALB | 중첩 로드밸런싱 |

### 리스너 (Listener)

ALB로 들어오는 요청의 **프로토콜과 포트를 확인하는 문지기**입니다.  
ALB를 생성하면 반드시 최소 하나 이상의 리스너가 필요합니다.

> **비유:** 공항 입구의 안내 데스크입니다.  
> "국내선이세요, 국제선이세요? (프로토콜 확인)" "몇 번 게이트로 가시나요? (포트 확인)"  
> 리스너는 이 첫 번째 관문 역할을 합니다. 관문을 통과한 승객을 어느 카운터 그룹(대상 그룹)으로 보낼지는 규칙이 결정합니다.

```
HTTP  80번 포트 리스너 → HTTP 요청만 받음
HTTPS 443번 포트 리스너 → HTTPS 요청만 받음
```

### 규칙 (Rule)

리스너를 통과한 트래픽을 **어디로, 어떻게 보낼지 결정**합니다.

하나의 규칙은 3가지 요소로 구성됩니다.

| 요소 | 내용 |
|---|---|
| **조건 (Condition)** | "만약 트래픽이 ~한 형태로 들어온다면" |
| **작업 (Action)** | "이렇게 처리해라" |
| **우선순위 (Priority)** | 겹치는 조건이 있을 때 먼저 검사할 순서 (숫자가 낮을수록 먼저 적용) |

**조건 예시:**

```
접속 호스트(Host) / 경로(Path) / 헤더(Header)
쿼리 스트링(Query String) / 소스 IP / HTTP 메서드
```

**작업 예시:**

```
Forward  → 특정 대상 그룹으로 전달
Redirect → 다른 URL로 리다이렉트 (HTTP → HTTPS 강제 전환 등)
Fixed Response → 고정 응답 메시지 반환 (404, 503 등)
```

---

## 리스너 규칙 실전 예시

### 리스너 1: HTTP 8080 포트 — 보안 및 접근 제어

```
규칙 우선순위 1:
  조건: 호스트 = *.awsclassroom.kr AND 소스 IP = 66.58.3.11
  작업: Private Blog 대상 그룹으로 Forward

규칙 우선순위 2:
  조건: 호스트 = *.awsclassroom.kr
  작업: 404 Fixed Response 반환
```

→ 특정 관리자 IP만 프라이빗 블로그 서버로 접속 가능, 나머지는 즉시 차단

### 리스너 2: HTTP 80 포트 — HTTPS 강제 리다이렉트

```
규칙 우선순위 1:
  조건: 호스트 = *.image.awsclassroom.kr
  작업: https://로 Redirect (301)
```

→ HTTP로 잘못 접속해도 자동으로 HTTPS로 전환

### 리스너 3: HTTPS 443 포트 — 호스트 기반 라우팅

```
규칙 우선순위 1:
  조건: 호스트 = *.image.awsclassroom.kr
  작업: 이미지 서버 대상 그룹으로 Forward

규칙 우선순위 2:
  조건: 호스트 = *.blog.awsclassroom.kr
  작업: Public Blog 대상 그룹으로 Forward
```

→ 접속한 서브도메인에 따라 알맞은 서버 그룹으로 트래픽 분산

## ALB 요금 구조 (LCU)

### 기본 요금 구조

```
ALB 총 요금 = 시간당 프로비전 비용 + LCU 사용량 비용
```

| 항목 | 서울 리전 기준 |
|---|---|
| 시간당 프로비전 비용 | 약 $0.0225 |
| LCU 단가 | 시간당 약 $0.008/LCU |

### LCU (Load Balancer Capacity Units) 란?

ALB가 트래픽을 얼마나 처리했는지 측정하는 단위입니다. 4가지 지표를 각각 측정합니다.

> **비유:** 공항 시설 사용료와 비슷합니다.  
> 공항은 게이트 점유 시간·처리 승객 수·수화물 무게·출입국 심사 횟수를 각각 측정하지만,  
> 청구는 그 중 가장 높게 나온 항목 하나만 기준으로 합니다.  
> ALB도 마찬가지입니다. 연결 수는 적어도 데이터가 많으면, 데이터 기준으로만 청구됩니다.

| 측정 지표 | 1 LCU 기준치 |
|---|---|
| 새로운 연결 (New Connections) | 초당 25개 |
| 활성 연결 (Active Connections) | 분당 3,000개 (TLS는 분당 1,500개) |
| 처리된 데이터 (Bytes) | 시간당 1GB (Lambda 대상은 0.4GB) |
| 규칙 평가 (Rule Evaluations) | 초당 1,000개 (기본 10개 룰 무료 제외) |

### 핵심 과금 원칙

> **4가지 지표 중 가장 높게 측정된 수치 하나만을 최종 과금 기준으로 삼습니다.**  
> (합산하지 않습니다)

### 요금 계산 예시

**시나리오:**
- 초당 1개의 새 연결이 들어와 2분간 유지됨
- 각 연결이 초당 5개 요청, 총 300KB/초 응답 발생
- 리스너 라우팅 규칙 총 60개 등록

**항목별 LCU 계산:**

| 지표 | 계산 | LCU |
|---|---|---|
| 새로운 연결 | 1개/초 ÷ 25 | **0.04** |
| 활성 연결 | 1개 × 2분 = 120개/분 ÷ 3,000 | **0.04** |
| 데이터 처리량 | 300KB/초 = 1.08GB/시간 ÷ 1 | **1.08** |
| 규칙 평가 | (60-10) × 5요청/초 = 250/초 ÷ 1,000 | **0.25** |

**최종 LCU:** 4가지 중 가장 높은 **1.08 LCU** (데이터 처리량)가 과금 기준

**최종 시간당 요금:** (1.08 × $0.008) + $0.0225 = **$0.03114**

## Amazon CloudWatch 모니터링

### CloudWatch 개요

AWS 리소스와 애플리케이션의 상태 및 성능을 실시간으로 관찰하는 모니터링 서비스입니다.

### EC2 모니터링: 기본 vs 세부

| 구분 | 기본 모니터링 | 세부 모니터링 |
|---|---|---|
| **비용** | 무료 | 유료 (지표 개수만큼 청구) |
| **데이터 수집 주기** | 5분 단위 | 1분 단위 |
| **활성화** | EC2 생성 시 자동 | 별도 활성화 필요 |

**기본 제공 지표:**

```
✅ CPU 사용률
✅ 디스크 읽기/쓰기
✅ 네트워크 트래픽 (In/Out)
✅ CPU 크레딧 (T 시리즈 인스턴스)
✅ 인스턴스 상태 확인 (1분 단위)
```

> **주의:** EC2의 **메모리(RAM) 사용량은 기본 지표로 제공되지 않습니다.**  
> 필요할 경우 CloudWatch Agent를 설치하여 '커스텀 지표'로 직접 올려보내야 합니다.  
>  
> **비유:** 관제탑 레이더로는 기체의 위치·고도·속도(CPU, 네트워크)는 기본으로 추적할 수 있지만,  
> 기내 연료 잔량(메모리)은 기체에 별도 계기판을 달아서 직접 보고받아야 하는 것과 같습니다.

### Auto Scaling 모니터링

별도로 모니터링 기능을 활성화해야 확인 가능합니다.

| 확인 가능한 정보 | 설명 |
|---|---|
| 그룹 용량 설정 | 현재 Min/Max/Desired 값 |
| 인스턴스 상태 | 정상 서비스 중인지, 이상이 있는지 |
| 통합 지표 | 그룹 전체 인스턴스의 합산 지표 |

Auto Scaling의 알람과 타겟 추적 스케일링 정책이 바로 이 CloudWatch 데이터를 바탕으로 작동합니다.

### ELB 모니터링

Auto Scaling과 달리 **기본적으로 활성화**되어 있습니다.

| 확인 가능한 정보 | 설명 |
|---|---|
| 전체 요청/연결 횟수 | 로드밸런서로 들어오는 트래픽 규모 |
| 상태 코드별 카운트 | 2xx(정상) / 4xx(클라이언트 오류) / 5xx(서버 오류) 각각 몇 번 |
| 처리된 트래픽 양 | 총 네트워크 처리 데이터 |
| IPv6 처리 내역 | IPv6 기반 요청 현황 |

## Auto Scaling + ELB 시너지

이 두 서비스가 결합되어야 클라우드의 진정한 강점이 발휘됩니다.

```
트래픽 급증
  → CloudWatch CPU 80% 알람
  → Auto Scaling: 인스턴스 5대 추가
  → ELB: 새로 생성된 5대를 즉시 감지하여 트래픽 분산 시작

인스턴스 장애
  → ELB Health Check 실패 감지
  → 해당 인스턴스로 트래픽 중단
  → Auto Scaling: 장애 인스턴스 교체 (새 인스턴스 자동 생성)
  → ELB: 새 인스턴스로 트래픽 다시 분산
```

무한한 확장성과 안정성(고가용성)은 Auto Scaling과 ELB의 연동으로 완성됩니다.
