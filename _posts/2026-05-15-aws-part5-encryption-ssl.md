## 암호화란?

> **비유:** 일기장에 자기만 아는 암호로 내용을 적어두는 것입니다.  
> 누군가 일기장을 훔쳐봐도 암호를 모르면 내용을 읽을 수 없습니다.

**암호화(Encryption)**는 수학적 알고리즘을 통해 데이터를 읽을 수 없는 형태로 변환하는 행위입니다.  
올바른 **키(Key)**를 가진 사람만 원래 데이터로 복원(복호화)할 수 있습니다.

### 암호화 vs 해시(Hash)

| 구분 | 암호화 | 해시 |
|---|---|---|
| 방향 | 양방향 (복원 가능) | 단방향 (복원 불가) |
| 용도 | 데이터 기밀 전송/저장 | 비밀번호 저장, 무결성 검증 |
| 예시 | AES, RSA | SHA-256, bcrypt |

> **해시 비유:** 고기를 다지면 다진 고기가 되지만, 다진 고기로 원래 고기 모양을 복원할 수 없는 것과 같습니다.  
> 비밀번호를 해시로 저장하면, DB가 털려도 원래 비밀번호를 알 수 없습니다.

---

## 주요 용어

| 용어 | 설명 |
|---|---|
| **평문 (Plaintext)** | 암호화하기 전 원본 데이터 |
| **암호문 (Ciphertext)** | 암호화된 결과물 (읽을 수 없음) |
| **암호화 (Encryption)** | 평문 → 암호문으로 변환하는 과정 |
| **복호화 (Decryption)** | 암호문 → 평문으로 되돌리는 과정 |
| **키 (Key)** | 암호화/복호화에 사용하는 핵심 값 (자물쇠의 열쇠) |
| **암호 알고리즘** | 암호화에 사용하는 수학적 규칙 (AES, RSA 등) |

## 암호화 적용 상황에 따른 분류

### Data at Rest (저장 데이터 암호화)

> **비유:** 집 금고에 돈을 넣어두는 것과 같습니다.  
> 금고(암호화)가 있으면, 누가 금고를 통째로 훔쳐가도 열쇠 없이는 못 씁니다.

- 디스크, DB에 저장할 때 암호화 적용
- 물리적 기기를 탈취당해도 데이터 유출 방지
- **AWS 예시:** S3 서버 사이드 암호화, RDS 암호화, EBS 암호화

### Data in Transit (전송 데이터 암호화)

> **비유:** 편지를 봉투에 넣고 봉인해서 보내는 것과 같습니다.  
> 중간에 집배원이 봉투를 열어봐도, 봉인이 되어 있으면 내용을 볼 수 없습니다.

- 네트워크를 통해 데이터를 전송할 때 암호화 적용
- 중간에서 패킷을 가로채도(중간자 공격) 내용을 읽을 수 없음
- **예시:** SSH, TLS, HTTPS

## 암호화 방식: 대칭키 vs 비대칭키

### 대칭키 암호화 (Symmetric Key)

> **비유:** 자물쇠와 열쇠가 하나만 있는 방식입니다.  
> 친구에게 보관함을 잠가서 보내려면, 열쇠도 함께 보내야 하는데 — 그 열쇠를 어떻게 안전하게 보낼지가 문제입니다.

```
평문 ──[같은 키]──► 암호문 ──[같은 키]──► 평문
```

- 암호화와 복호화에 **동일한 키 하나**를 사용
- **장점:** 연산이 가볍고 빠름 (대용량 데이터 암호화에 적합)
- **단점:** 키를 상대방에게 안전하게 전달하는 방법이 문제 (키 배송 문제)
- **대표 알고리즘:** AES, DES

### 비대칭키 암호화 (Asymmetric Key)

> **비유:** 우편함과 같습니다.  
> 우편함에는 누구나 편지를 넣을 수 있지만(공개키로 암호화),  
> 꺼내서 읽을 수 있는 건 열쇠(비밀키)를 가진 집주인뿐입니다.

```
공개키(Public Key)로 암호화 → 비밀키(Private Key)로만 복호화 가능
비밀키(Private Key)로 암호화 → 공개키(Public Key)로만 복호화 가능
```

- **한 쌍의 키(공개키 + 비밀키)**를 사용
- 공개키는 누구에게나 배포 가능 → 키 배송 문제 해결
- **장점:** 키 관리가 편리 (공개키는 공개해도 됨)
- **단점:** 대칭키보다 연산이 복잡하고 느림
- **대표 알고리즘:** RSA, ECC

## 디지털 서명 (Digital Signature)

> **비유:** 계약서에 도장을 찍는 것과 같습니다.  
> "이 문서는 내가 작성했고, 중간에 변조되지 않았다"는 것을 증명합니다.

- 데이터가 **진짜 해당 발신자**에 의해 만들어졌음을 보장(인증)하는 방법입니다.
- 발신자가 **비밀키(Private Key)**로 서명 생성 → 수신자가 **공개키(Public Key)**로 서명 검증

```
[서명 생성] 데이터 ──[내 Private Key]──► 서명(Signature)
[서명 검증] 서명 ──[발신자 Public Key]──► 유효하면 "진짜" 확인!
```

**서명이 보장하는 것:**
- **인증(Authentication):** 이 데이터를 보낸 게 진짜 그 사람인가?
- **무결성(Integrity):** 데이터가 중간에 변조되지 않았는가?

## SSL / TLS

> **비유:** 두 사람이 처음 만나 서로 신분증을 확인하고, 앞으로 쓸 암호를 정한 뒤 비밀 대화를 나누는 것과 같습니다.

**SSL(Secure Sockets Layer)** / **TLS(Transport Layer Security)**는 클라이언트와 서버 간의 통신을 **암호화**하여 데이터의 기밀성과 무결성을 보장하는 보안 프로토콜입니다.

- SSL은 구버전, TLS는 그 후속 버전 (현재 TLS 1.3이 최신)
- 이 프로토콜이 적용된 HTTP가 바로 **HTTPS**

### HTTP vs HTTPS

| 구분 | HTTP | HTTPS |
|---|---|---|
| 암호화 | 없음 (평문) | TLS로 암호화 |
| 포트 | 80 | 443 |
| 보안 | 중간자 공격에 취약 | 안전 |
| 인증서 | 불필요 | SSL/TLS 인증서 필요 |
| 주소창 | `http://` | `https://` + 🔒 |

## TLS Handshake (연결 수립 과정)

> **비유:** 처음 만나는 외국인과 대화하기 위해,  
> ① 서로 쓸 수 있는 언어를 확인하고  
> ② 상대방 신분증을 확인한 뒤  
> ③ 앞으로 쓸 암호 체계를 정하는 과정입니다.

```
클라이언트                              서버
    │                                    │
    │──── ClientHello (지원 TLS 버전, 암호 목록) ────►│
    │                                    │
    │◄─── ServerHello (선택된 알고리즘) ────────────│
    │◄─── Certificate (서버 인증서) ────────────────│
    │                                    │
    │ [인증서 검증: CA 서명 확인]         │
    │                                    │
    │──── 키 교환 메시지 ─────────────────────────►│
    │                                    │
    │◄────────── 암호화된 통신 시작 ──────────────►│
```

### 3단계 상세 설명

**① Cipher Suites 교환**
- 클라이언트가 "나 이런 알고리즘들 쓸 수 있어" 목록을 보냄
- 서버가 그 중 자신도 지원하는 알고리즘을 선택해 응답
- 앞으로 쓸 암호화 방식을 협의하는 과정

**② 인증서 검증 (Certificate)**
- 서버가 자신의 **SSL 인증서**를 클라이언트에게 보냄
- 인증서에는 서버의 공개키와 **CA(인증기관)의 디지털 서명**이 포함됨
- 클라이언트는 신뢰할 수 있는 CA 목록(브라우저에 내장)으로 서명을 검증

> **CA(Certificate Authority) 비유:**  
> 정부가 발급하는 여권과 같습니다.  
> 여권(인증서)을 보면 "정부(CA)가 이 사람이 진짜 홍길동임을 보증한다"는 것을 알 수 있습니다.

**③ 키 교환 (Session Key 생성)**
- 비대칭키(느리지만 안전)로 대칭키(빠름)를 안전하게 교환
- 이후 실제 통신은 이 **세션 키(대칭키)**로 암호화 → 속도와 보안 모두 확보

```
[왜 대칭키+비대칭키를 혼합할까?]
비대칭키만 쓰면: 안전하지만 너무 느림
대칭키만 쓰면: 빠르지만 키 배송 문제
혼합 사용: 비대칭키로 대칭키를 안전하게 교환 → 이후 대칭키로 빠르게 통신
```

## AWS에서의 암호화

| 서비스 | 암호화 방식 |
|---|---|
| **ACM (AWS Certificate Manager)** | SSL/TLS 인증서 발급 및 관리 |
| **KMS (Key Management Service)** | 암호화 키 생성·관리·교체 자동화 |
| **S3 암호화** | 서버 사이드 암호화 (SSE-S3, SSE-KMS) |
| **RDS 암호화** | 저장 데이터 자동 암호화 |
| **CloudFront + ACM** | HTTPS 배포 (CDN + TLS 인증서) |
