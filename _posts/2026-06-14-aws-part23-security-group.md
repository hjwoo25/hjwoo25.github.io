---

## 보안 그룹(Security Group)의 개념과 특징

> **비유:** 서버마다 배치된 철저한 개인 경호원입니다.  
> 기본적으로 아무도 접근하지 못하게 꽉 막고 있다가, 명단(Rule)에 있는 사람(Source IP)이 약속된 목적(Port)으로 왔을 때만 문을 열어줍니다.  
> "A라는 사람은 절대 안 돼(Deny)"라고 막을 수는 없고, 그냥 "B, C만 들어와(Allow)"라고 설정하는 방식입니다.

보안 그룹은 인스턴스(서버)에 들어오고(Inbound) 나가는(Outbound) 트래픽을 제어하는 **가상 방화벽** 역할을 합니다.

### 핵심 특징 정리

| 항목 | 내용 |
|---|---|
| **방어 단위** | 인스턴스 단위 (정확히는 ENI — 네트워크 인터페이스 단위) |
| **다중 적용** | 하나의 인스턴스에 여러 보안 그룹을 동시에 적용 가능 (규칙이 합쳐져 적용) |
| **포트 제어 방식** | **White List** 방식 — 기본적으로 모든 포트가 닫혀 있고, 허용만 설정 가능 |
| **Deny 규칙** | 불가능 (명시적 차단은 NACL에서만 가능) |
| **관리 범위** | VPC 단위로 생성 및 관리 (VPC 간 공유 기능으로 여러 VPC에서 사용 가능) |

## Stateful (상태 유지) — 가장 중요한 개념

보안 그룹은 **Stateful** 방식으로 동작합니다. 이것이 시험이나 실무에서 가장 핵심적인 포인트입니다.

### Stateful이란?

인바운드(Inbound) 규칙을 통과해서 무사히 들어온 트래픽은, 나갈 때(Outbound) **별도의 허용 설정이 없어도 무사히 나갈 수 있습니다.** 즉, 들어올 때 얼굴을 튼 손님은 나갈 때 프리패스입니다.

### 동작 예시

```
[클라이언트: 175.121.214.107]
    │
    │  요청: 임시 포트(56630) → 서버의 80번 포트(HTTP)
    ▼
[서버: 13.124.105.122]  ← 보안 그룹: 인바운드 80 포트 허용
    │
    │  응답: 서버 → 클라이언트의 임시 포트(56630)
    │  ✅ 아웃바운드 규칙이 none이어도 통과!
    ▼
[클라이언트: 175.121.214.107]
```

- 서버의 보안 그룹이 **인바운드 80 포트를 허용**해 두었으므로 요청이 들어옵니다.
- 아웃바운드 규칙이 **다 막혀(none) 있더라도**, 서버가 응답을 돌려보낼 때는 방금 들어온 클라이언트의 임시 포트(56630)를 **기억하고 있기 때문에** 문제없이 나갑니다.

### 비교: NACL은 Stateless

서브넷 방화벽인 NACL은 매정하게도 **상태를 기억하지 않습니다.** 들어오는 규칙(Inbound)과 나가는 규칙(Outbound)을 **각각 따로따로 허용**해 주어야만 통신이 성립합니다.

| 항목 | 보안 그룹 (Stateful) | NACL (Stateless) |
|---|---|---|
| 들어온 트래픽의 응답 | 자동 허용 | 별도 아웃바운드 규칙 필요 |
| 나간 트래픽의 응답 | 자동 허용 | 별도 인바운드 규칙 필요 |

## 출발지(Source) 설정 방법

"누구를 통과시켜 줄 것인가?"를 설정할 때 다양한 방식을 사용할 수 있습니다.

| 설정 방식 | 예시 | 설명 |
|---|---|---|
| **IP Range (CIDR)** | `10.0.0.0/24` | 특정 IP 대역 전체를 통째로 허용 |
| **접두사 목록 (Prefix List)** | `pl-123456` | 여러 IP를 하나로 묶어둔 리스트 |
| **다른 보안 그룹 참조** | `sg-0abc1234` | IP 대신 보안 그룹 이름을 소스로 지정 |

---

## 접두사 목록 (Prefix List) 활용

보안 그룹 규칙에 수십 개의 IP를 일일이 적기 힘들 때 사용하는 **"단축어 리스트"**입니다.

### 종류

| 종류 | 설명 | 수정 가능 |
|---|---|---|
| **고객 관리형** | 사용자가 직접 IP 목록을 만들고 수정, 다른 계정과 공유 가능 | ✅ |
| **AWS 관리형** | AWS가 자체 서비스(DynamoDB, S3, CloudFront 등)의 IP 목록을 묶어둔 것 | ❌ |

### 주의사항

- IPv4와 IPv6를 **한 목록에 섞어 쓸 수 없음**
- 생성 시점에 **최대 엔트리(목록 개수)를 지정**해야 함

### 활용 예시

5개의 서로 다른 IP 주소(`152.3.83.1` 등)를 허용해야 할 때:

```
[Before] 보안 그룹에 일일이 5줄씩 작성
  SeG-EC2: 152.3.83.1, 110.5.2.3, ...
  SeG-RDS: 152.3.83.1, 110.5.2.3, ...

[After] 접두사 목록 활용
  Prefix List (pl-123456) = [152.3.83.1, 110.5.2.3, ...]
  SeG-EC2 소스: pl-123456  ← 딱 한 줄
  SeG-RDS 소스: pl-123456  ← 딱 한 줄
```

## 보안 그룹 참조 (Security Group Referencing) — 실무 끝판왕

> **비유:** 파티장(DB 서버) 입구에서 경호원(보안 그룹)이 주민등록번호(IP 주소)가 적힌 명단을 들고 일일이 대조하는 것이 아닙니다.  
> 대신 **"가슴에 '삼성전자 직원(SeG-EC2 보안 그룹)' 명찰 달고 있네? 사원증 맞네. 통과!"**라고 소속(그룹)만 보고 문을 열어주는 스마트한 방식입니다.

IP 주소가 계속 변하는 클라우드 환경에서 매우 유용한 기능입니다.

### 문제 상황

- 웹 서버용 그룹(SeG-EC2) 수십 대와 DB 서버용 그룹(SeG-RDS)이 있습니다.
- DB 서버는 오직 우리의 웹 서버들**만** 접근하게 허용해야 합니다.
- 그런데 웹 서버가 **Auto Scaling**으로 늘어났다 줄어들 때마다 IP가 계속 바뀝니다.

### 해결책

DB 서버의 인바운드 규칙(소스)에 특정 IP를 적지 않고, 웹 서버의 **보안 그룹 이름(SeG-EC2) 자체**를 입력합니다.

```
[SeG-RDS 인바운드 규칙]
  포트: 3306 (MySQL)
  소스: SeG-EC2  ← IP가 아닌 보안 그룹!

→ SeG-EC2 명찰을 단 서버라면 IP가 뭐든 DB 접근 허용!
```

### 효과

웹 서버의 IP가 아무리 수시로 바뀌더라도, **SeG-EC2라는 보안 그룹이 적용된 서버라면 무조건 DB 서버로 통과**가 허용됩니다.

### CloudFront + Load Balancer 활용 예시

```
사용자 → CloudFront → Load Balancer(SeG-ELB) → EC2(Auto Scaling)

[EC2 보안 그룹 인바운드 규칙]
  소스: SeG-ELB  ← Load Balancer의 보안 그룹 참조

→ 사용자가 직접 EC2로 뚫고 들어올 수 없음
→ 오직 Load Balancer를 통과한 트래픽만 EC2에 도달
```
