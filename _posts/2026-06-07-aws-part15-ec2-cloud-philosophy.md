클라우드 환경에서 EC2를 단순히 "서버 하나 빌리는 것"으로 이해하면 금방 한계에 부딪힙니다.  
온프레미스(물리 서버)와 클라우드의 근본적인 차이, 그리고 올바른 아키텍처 설계 철학을 정리합니다.

---

## 인스턴스 확장(Scaling) 방식의 차이

서버 성능을 올리는 방법은 크게 두 가지입니다.

### 수직 확장 (Scale Up / Vertical Scale)

기존 서버의 사양(CPU, RAM 등) 자체를 더 높은 등급으로 교체하는 방식입니다.

> **비유:** 승객이 늘자 소형 비행기를 점보제트기로 교체하는 방식입니다.  
> 한계는 명확합니다. 비행기가 커질수록 가격은 기하급수적으로 오르고, 세상에서 가장 큰 비행기에도 좌석 수는 한계가 있습니다.

```
t3.micro → t3.large → c5.4xlarge → ...
```

| 장점 | 단점 |
|---|---|
| 기존 아키텍처 변경 없음 | 성능 대비 비용이 기하급수적으로 증가 |
| 빠른 적용 | 단일 하드웨어 물리적 한계 존재 |
| | 서버 한 대에 의존 → 장애 시 서비스 전체 다운 |

### 수평 확장 (Scale Out / Horizontal Scale)

동일한 사양의 서버(인스턴스) '대수'를 여러 대로 늘리는 방식입니다.

> **비유:** 점보제트기 대신, 같은 기종 비행기 편수를 늘리는 방식입니다.  
> 1대가 300명을 못 태워도, 10대가 각각 나눠서 태우면 됩니다.  
> 1대가 결항해도 나머지 9대가 계속 운항합니다.

```
t3.medium × 1대 → t3.medium × 10대 → t3.medium × 100대 → ...
```

| 장점 | 단점 |
|---|---|
| 비용이 대수에 정비례하여 합리적 | 트래픽 분산 구조(로드밸런서) 필요 |
| 이론상 무한 확장 가능 | 애플리케이션이 Stateless해야 함 |
| 일부 장애 시 서비스 지속 가능 | |

클라우드에서는 **수평 확장**이 기본 전략입니다.

## 탄력성 (Elasticity)

> **"고정된 자원을 쓰는 것이 아니라, 수요에 따라 유연하게 늘리고 줄인다"**

> **비유:** 항공사의 성수기·비수기 편수 조정과 같습니다.  
> 온프레미스 방식이라면 여름 성수기 기준으로 비행기를 구매해 두고, 비수기에도 빈 좌석인 채로 계속 운항해야 합니다.  
> 클라우드 방식은 여름엔 임시편을 대거 투입하고, 겨울 비수기엔 운항 편수를 줄여 비용을 아낍니다.

온프레미스에서는 최대 트래픽 시나리오를 기준으로 서버를 구매합니다.  
평소에는 서버 대부분이 놀고 있어도, 구매한 비용은 그대로 지출됩니다.

클라우드의 탄력성은 이 문제를 해결합니다.

```
평일 새벽 2시:  EC2 × 2대  (트래픽 적음)
평일 오후 12시: EC2 × 10대 (점심 트래픽 증가)
대규모 이벤트:  EC2 × 50대 (급격한 트래픽 대응)
이벤트 종료:    EC2 × 5대  (자동 축소)
```

→ 실제 사용한 만큼만 비용이 발생합니다.

## 클라우드 컴퓨팅의 핵심 철학: 대체 가능성

> **"Everything fails, all the time."**  
> — Werner Vogels (AWS CTO)

> **비유:** 항공사는 특정 기체 번호에 집착하지 않습니다.  
> 'HL7234' 기체가 정비 들어가면 즉시 'HL8901' 기체로 교체해 같은 노선을 운항합니다.  
> 승객은 어느 기체를 탔는지 모르고, 알 필요도 없습니다. 중요한 것은 노선이 정상 운항되는 것입니다.  
> 온프레미스 서버는 기체 번호를 기억하고 애지중지 관리하는 것, EC2는 기체가 바뀌어도 노선이 이어지면 그만인 것입니다.

### 온프레미스 vs 클라우드의 서버 관리 관점 차이

| 구분 | 온프레미스 | 클라우드 |
|---|---|---|
| 서버를 보는 관점 | 반영구적 자산 (애지중지 관리) | 소모품 (언제든 교체 가능) |
| 장애 대응 | 서버 살리기에 집중 | 새 인스턴스로 즉시 교체 |
| 설계 방향 | 장애가 나지 않도록 | 장애가 나도 서비스는 유지 |

### 핵심 전제

**"EC2 인스턴스는 언제든 예고 없이 종료될 수 있다"** 는 것을 기본으로 깔고 시스템을 설계해야 합니다.

하드웨어 장애, AWS 점검, Spot 인스턴스 회수 등 다양한 이유로 인스턴스가 갑자기 사라질 수 있습니다.  
중요한 것은 **인스턴스가 없어져도 서비스는 계속 돌아가는 구조**를 만드는 것입니다.

## 고가용성과 Stateless (상태 비저장)

서버가 언제든 죽을 수 있다는 전제 아래 안정적인 서비스를 유지하려면 두 가지가 필수입니다.

### Stateless (상태 비저장)

특정 EC2 인스턴스 내부에 중요한 데이터나 상태 정보를 저장하지 않는 설계 방식입니다.

> **비유:** 탑승권 정보는 특정 체크인 카운터 직원 머릿속에 있는 게 아니라 항공사 중앙 서버에 저장되어 있습니다.  
> 그래서 1번 카운터 직원이 자리를 비워도, 2번 카운터에서 그대로 탑승 수속을 이어받을 수 있습니다.  
> EC2도 마찬가지입니다. 데이터를 외부(RDS, S3)에 두면, 어떤 인스턴스가 교체되어도 서비스는 끊기지 않습니다.

**Stateful 구조의 문제:**

```
User A ─→ EC2-1 (세션 저장) ─→ EC2-1 장애 → User A의 세션 사라짐 😱
User B ─→ EC2-2 (파일 업로드) ─→ EC2-2 종료 → 파일 사라짐 😱
```

**Stateless 구조:**

```
User A ─→ EC2-1 ──→ 세션: ElastiCache(Redis)
User B ─→ EC2-2 ──→ 파일: S3
               ──→ DB:   RDS

EC2-1 장애 → EC2-3으로 즉시 대체 → 세션·파일 그대로 유지 ✅
```

인스턴스가 상태 정보를 쥐고 있지 않아야, 해당 인스턴스가 삭제되거나 새 인스턴스가 추가되어도 서비스에 지장이 없습니다.

### 고가용성 (High Availability)

수많은 인스턴스 중 일부가 다운되더라도 시스템 전체가 정상 작동하며, 다운된 수만큼 자동으로 복구(대체)되는 능력입니다.

> **비유:** 같은 노선에 여러 편이 뜨는 이유입니다.  
> 오전 9시 편이 결항해도 오전 11시 편이 승객을 태우고, Auto Scaling이 결항한 편을 즉시 대체 투입합니다.  
> 승객(사용자)은 잠깐 기다릴 수도 있지만, 아예 목적지에 못 가는 일은 없습니다.

```
AZ-a: EC2 × 3대  ─→  1대 다운 → Auto Scaling이 자동으로 1대 추가
AZ-b: EC2 × 3대  ─→  2대 다운 → Auto Scaling이 자동으로 2대 추가

전체 서비스: 중단 없이 계속 운영 ✅
```

## 성공적인 EC2 활용을 위한 아키텍처 조합

EC2 단일 서비스만 띄워놓는 것은 클라우드를 제대로 활용하는 것이 아닙니다.

```
                    ┌─────────────────────────┐
사용자 트래픽 ──→   │   Elastic Load Balancer  │
                    └─────────────┬───────────┘
                                  │ 트래픽 분산
              ┌───────────────────┼───────────────────┐
              ↓                   ↓                   ↓
         [EC2 인스턴스]      [EC2 인스턴스]      [EC2 인스턴스]
              │                   │                   │
              └───────────────────┴───────────────────┘
                                  │
              ┌───────────────────┼───────────────────┐
              ↓                   ↓                   ↓
           [RDS]              [S3/EFS]          [ElastiCache]
          (데이터베이스)       (파일 저장)         (세션/캐시)

                    ↑ Auto Scaling이 EC2 개수 자동 조절
```

| 서비스 | 역할 |
|---|---|
| **Auto Scaling** | 트래픽/장애 상태에 따라 EC2를 자동으로 켜고 끔 |
| **Elastic Load Balancer** | 여러 EC2 인스턴스로 트래픽 고르게 분산 |
| **RDS** | EC2 외부 독립 데이터베이스 (Stateless 유지) |
| **S3 / EFS** | EC2 외부 독립 파일 스토리지 (Stateless 유지) |

이 4가지 서비스가 EC2와 함께 맞물려야 클라우드의 진정한 강점인 **고가용성·탄력성·비용 효율**을 달성할 수 있습니다.
