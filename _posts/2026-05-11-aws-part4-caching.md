## 캐싱(Caching)이란?

> **비유:** 수학 시험을 볼 때, 자주 쓰는 공식을 매번 유도하지 않고 공식집에 적어뒀다가 바로 꺼내 쓰는 것과 같습니다.  
> 컴퓨터도 자주 요청되는 데이터를 매번 원본에서 가져오는 대신, 빠른 임시 저장소에 복사해두고 즉시 응답합니다.

**캐싱(Caching)**은 데이터의 복제본이나 복잡한 연산 결과를 임시로 저장해두고, 동일한 요청이 왔을 때 원본에 접근하지 않고 즉시 응답하는 기술입니다.

```
[캐시 없을 때]
사용자 → 서버 → DB → 연산 → 서버 → 사용자 (느림 😩)

[캐시 있을 때]
사용자 → 캐시 → 사용자 (빠름 😊)
```

---

## 장점과 단점

### 장점

- **속도 향상:** 메모리(RAM) 기반 캐시는 디스크 기반 DB보다 수백~수천 배 빠릅니다.
- **서버 부하 감소:** DB에 쿼리가 줄어 원본 서버 부담이 크게 줄어듭니다.
- **비용 절감:** DB 연산 횟수가 줄어 인프라 비용을 절감할 수 있습니다.

### 단점

- **데이터 불일치 (Consistency):** 원본 데이터가 바뀌었는데 캐시는 아직 오래된 데이터를 갖고 있을 수 있습니다.
- **구조 복잡도 증가:** 캐시 레이어가 추가되면 시스템이 더 복잡해집니다.
- **추가 비용:** 캐시 서버(주로 메모리 기반) 운영 비용이 발생합니다.

---

## 핵심 개념

| 용어 | 설명 | 비유 |
|---|---|---|
| **원본 (Origin)** | 실제 데이터가 있는 DB나 서버 | 도서관 원본 서고 |
| **캐시 히트 (Cache Hit)** | 요청 데이터가 캐시에 있어 즉시 응답 | 복사본이 카운터에 있어 바로 줌 |
| **캐시 미스 (Cache Miss)** | 캐시에 없어서 원본에서 가져와야 함 | 서고까지 직접 가야 함 |
| **TTL (Time To Live)** | 캐시 데이터의 유효 시간 | 음식의 유통기한 |
| **캐시 만료 (Eviction)** | 공간 확보나 최신화를 위해 캐시 데이터 삭제 | 유통기한 지난 음식 버리기 |

## 캐싱 읽기 전략 (Loading Strategies)

### Lazy Loading (지연 로딩)

> **비유:** 손님이 주문한 메뉴만 준비하는 식당 방식입니다.  
> 주문이 없으면 만들지 않으니 낭비는 없지만, 첫 손님은 기다려야 합니다.

```
요청 → 캐시 확인 → 캐시 미스 → 원본에서 조회 → 캐시에 저장 → 응답
                → 캐시 히트 → 즉시 응답
```

- **장점:** 실제로 요청된 데이터만 캐싱 → 메모리 낭비 없음
- **단점:** 최초 요청 시 반드시 캐시 미스 발생 → 응답 지연 (Cold Start)
- **사용 상황:** 어떤 데이터가 자주 쓰일지 예측하기 어려울 때

### Eager Loading (즉시 로딩 / 사전 캐싱)

> **비유:** 편의점 냉장고처럼, 미리 모든 음료를 채워놓는 방식입니다.  
> 손님이 오면 바로 줄 수 있지만, 인기 없는 음료도 채워야 하니 공간 낭비가 생깁니다.

- **장점:** 첫 요청도 캐시 히트 → 빠른 응답
- **단점:** 불필요한 데이터도 미리 캐싱 → 메모리 낭비, 초기 로딩 비용 큼
- **사용 상황:** 사용될 데이터가 명확히 정해진 경우 (예: 메인 페이지 배너 이미지)

## 캐싱 쓰기 전략 (Write Strategies)

### Write-Through (동시 쓰기)

> **비유:** 노트에 필기하면서 동시에 클라우드에도 자동 저장하는 것처럼, 캐시와 원본을 항상 함께 업데이트합니다.

```
쓰기 요청 → 캐시에 저장 + 원본 DB에 저장 (동시)
```

- **장점:** 캐시와 원본이 항상 일치 → 일관성(Consistency) 완벽 보장
- **단점:** 매 쓰기마다 두 곳에 저장 → 쓰기 속도 느림

### Write-Back (지연 쓰기)

> **비유:** 일단 메모장에 빠르게 적어두고, 나중에 정리된 노트에 옮겨 적는 것과 같습니다.

```
쓰기 요청 → 캐시에만 저장 (빠름) → 나중에 원본 DB에 반영
```

- **장점:** 쓰기 속도가 매우 빠름
- **단점:** 캐시 서버 장애 시 아직 원본에 쓰지 않은 데이터 유실 가능

## 캐시 만료 정책 (Eviction Policies)

캐시 공간이 꽉 찼을 때 어떤 데이터를 먼저 지울지에 대한 정책입니다.

| 정책 | 설명 | 비유 |
|---|---|---|
| **TTL** | 일정 시간 지나면 무조건 삭제 | 유통기한 지나면 버림 |
| **LRU** (Least Recently Used) | 가장 오래 전에 사용한 데이터부터 삭제 | 오랫동안 안 꺼낸 물건부터 버림 |
| **LFU** (Least Frequently Used) | 사용 횟수가 가장 적은 데이터부터 삭제 | 가장 덜 읽은 책부터 버림 |
| **FIFO** | 가장 먼저 들어온 데이터부터 삭제 | 먼저 들어온 줄 먼저 내보냄 |

> **LRU vs LFU 차이:**  
> - LRU: "최근에 사용된 적 없으면 제거" → 최신 사용 패턴 반영 (Redis 기본값)  
> - LFU: "전체 사용 횟수가 적으면 제거" → 과거에만 반짝 인기 있었던 데이터를 더 잘 제거

## 주요 사용 사례

### CDN (Content Delivery Network)

> **비유:** 전국 물류창고 네트워크와 같습니다.  
> 서울 본사 창고에서 부산까지 보내는 대신, 부산 물류 센터에 미리 재고를 쌓아두면 빠르게 배송할 수 있습니다.

- 전 세계 **엣지 서버**에 정적 파일(이미지, JS, CSS, 동영상)을 미리 캐싱합니다.
- 사용자는 멀리 있는 원본 서버 대신 **가까운 엣지 서버**에서 파일을 받습니다.
- **AWS CloudFront**가 대표적인 CDN 서비스입니다.

```
[CDN 없을 때] 한국 사용자 ──────────── 미국 서버 (느림 😩)
[CDN 있을 때] 한국 사용자 → 서울 엣지 서버 (빠름 😊)
```

### ElastiCache (Redis / Memcached)

- AWS에서 제공하는 **인메모리 캐시 서비스**입니다.
- 주 사용 사례:
  - **로그인 세션 저장** (사용자 로그인 상태 유지)
  - **랭킹 보드** (실시간 순위 데이터)
  - **자주 조회되는 DB 쿼리 결과 캐싱** (예: 상품 목록, 메인 배너)
  - **분산 락(Distributed Lock)** (동시 요청 제어)

| 구분 | Redis | Memcached |
|---|---|---|
| 데이터 구조 | 다양 (String, List, Set, Hash...) | 단순 (Key-Value) |
| 영속성 | 디스크 저장 가능 | 메모리만 (서버 끄면 사라짐) |
| 클러스터 | 지원 | 제한적 |
| 주 사용 | 세션, 랭킹, pub/sub | 단순 캐시 |

### HTTP 캐시 헤더

웹 브라우저도 자체적으로 파일을 캐싱합니다. 서버가 응답 시 HTTP 헤더로 캐시 정책을 지정합니다.

```http
Cache-Control: max-age=86400        # 24시간 캐시
Cache-Control: no-cache             # 항상 서버에 유효성 검사
Cache-Control: no-store             # 캐시 저장 금지
ETag: "abc123"                      # 파일 버전 식별자 (변경 여부 확인용)
```

> **💡 ETag 동작 방식:**  
> 브라우저가 파일을 재요청할 때 "내가 가진 파일이 ETag abc123인데, 변경됐어?"라고 물어보면  
> 서버가 "안 변했어!" → `304 Not Modified` (파일을 다시 보내지 않음, 빠름)  
> 서버가 "바뀌었어!" → `200 OK` + 새 파일 전송

### RAM (메모리)

- 하드디스크(SSD/HDD)와 CPU 사이에서 **속도 차이를 극복**하는 하드웨어적 캐시입니다.
- CPU가 파일을 읽을 때마다 디스크에서 가져오면 너무 느리니, RAM에 임시 저장해 빠르게 접근합니다.

---

## 정리: 어디서 캐싱이 일어나고 있나?

```
사용자 브라우저 (HTTP 캐시)
    ↓
CDN 엣지 서버 (CloudFront)
    ↓
로드 밸런서
    ↓
애플리케이션 서버 (로컬 인메모리 캐시)
    ↓
ElastiCache (Redis)
    ↓
DB (쿼리 캐시)
    ↓
디스크 (OS 파일 캐시)
```

캐싱은 한 곳이 아니라 **시스템의 여러 레이어**에서 동시에 일어납니다!
