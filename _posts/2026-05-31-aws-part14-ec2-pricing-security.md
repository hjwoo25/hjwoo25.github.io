EC2를 제대로 활용하려면 두 가지를 반드시 알아야 합니다.  
**요금 모델** — 어떤 방식으로 쓸 때 가장 비용을 아낄 수 있는가,  
**보안 그룹** — 인스턴스를 어떻게 외부 위협으로부터 보호하는가.

---

## EC2 요금 철학

> **AWS의 가격 철학:** "미리 내지 않고, 사용한 만큼 내고, 예약할수록 더 적게 낸다."

EC2 요금은 크게 4가지 항목으로 구성됩니다.

| 항목 | 설명 |
|---|---|
| **인스턴스 요금** | 실행 시간(초/시간)에 따른 컴퓨팅 비용 |
| **데이터 전송** | 인터넷 아웃바운드 트래픽 비용 |
| **공인 IP** | Elastic IP 등 고정 IP 사용 비용 |
| **연동 서비스** | EBS, ELB, CloudWatch 등 사용량 |

---

## 요금 모델 5가지

### ① 온디맨드 (On-Demand)

> **비유:** 편의점처럼 정가에 원할 때 사고, 쓴 만큼만 냅니다.

- **약정 없음**, 언제든 시작하고 중지 가능
- 실행한 **초/시간 단위**로만 비용 납부
- 수요 예측이 어렵거나 **단기/비정기 워크로드**에 최적

```
사용 예:
- 갑자기 늘어난 트래픽 대응
- 개발/테스트 환경 (필요할 때만 켜고 끄기)
- 처음 AWS를 시작해서 사용량을 파악 중일 때
```

---

### ② 예약 인스턴스 (Reserved Instances)

> **비유:** 헬스장 연간 회원권. 매달 내는 것보다 저렴하지만, 1년치를 선납해야 합니다.

- **특정 리전 + 인스턴스 유형**을 1년 또는 3년 약정
- 온디맨드 대비 **최대 72% 할인**
- 약정 기간 동안 사용 여부와 관계없이 비용 발생

```
온디맨드 월 $100 → 예약 인스턴스 (3년, 전액 선납) 월 약 $28 ✅

단, 1년/3년 동안 같은 인스턴스 유형을 쓸 것이 확실할 때만 유리 ⚠️
```

**예약 인스턴스 옵션:**

| 옵션 | 설명 |
|---|---|
| **Standard RI** | 할인율 최대, 인스턴스 유형 변경 불가 |
| **Convertible RI** | 할인율 낮음, 인스턴스 유형 변경 가능 |

---

### ③ Savings Plan

> **비유:** 예약 인스턴스가 "특정 헬스장 연간권"이라면, Savings Plan은 **전국 헬스장 이용 가능한 프리미엄 연간권**입니다.

- 인스턴스 단위가 아닌 **'컴퓨팅 파워 사용량' 자체를 약정**하는 모델
- 최대 **72% 저렴**하게 이용 가능
- 예약 인스턴스보다 **유연성이 높음** (인스턴스 패밀리, 리전, OS 변경 자유)

```
예약 인스턴스: "서울 리전의 c5.xlarge를 1년간 쓰겠습니다"
Savings Plan: "한 달에 $50어치의 컴퓨팅을 1년간 쓰겠습니다"
              → 어떤 인스턴스, 어떤 리전이든 약정 금액 내에서 자유롭게 사용
```

---

### ④ 스팟 인스턴스 (Spot Instance)

> **비유:** 비행기 빈 좌석을 파격 할인에 판매하는 것처럼, AWS의 **남는 컴퓨팅 자원을 싸게 사용**합니다.

- AWS에 남는 잉여 컴퓨팅 자원 활용
- 온디맨드 대비 **최대 90% 저렴**
- **단점:** AWS 상황에 따라 인스턴스가 **언제든 중단**될 수 있음 (2분 전 통보)

```
사용 가능한 워크로드 (중단되어도 괜찮은 것):
✅ 머신러닝 모델 학습 (체크포인트로 이어서 가능)
✅ 배치 데이터 처리
✅ CI/CD 빌드 파이프라인

부적합한 워크로드:
❌ 실시간 웹서버 (중단 시 서비스 장애)
❌ 데이터베이스 (데이터 손실 위험)
```

---

### ⑤ 전용 인스턴스 / 전용 호스트 (Dedicated)

> **비유:** 호텔 일반 객실(공유) 대신 **통째로 전세낸 독채**를 사용합니다.

- **물리적으로 완전히 격리된 하드웨어** 서버를 단독으로 임대
- 다른 AWS 고객과 하드웨어를 공유하지 않음

**사용 이유:**

| 이유 | 설명 |
|---|---|
| **규정 준수** | 금융·의료 등 법적으로 단독 서버 요구 시 |
| **소프트웨어 라이선스** | 특정 Oracle, Windows 라이선스가 소켓/코어 수 기준일 때 |
| **퍼포먼스 격리** | 다른 고객 워크로드의 영향을 전혀 받지 않아야 할 때 |

---

## 요금 모델 비교 요약

| 모델 | 약정 | 할인율 | 유연성 | 적합한 상황 |
|---|---|---|---|---|
| 온디맨드 | 없음 | 없음 | 최고 | 단기, 예측 불가 워크로드 |
| 예약 인스턴스 | 1~3년 | 최대 72% | 낮음 | 장기 고정 워크로드 |
| Savings Plan | 1~3년 | 최대 72% | 중간 | 장기이나 인스턴스 유연성 필요 |
| 스팟 | 없음 | 최대 90% | 낮음 (중단 가능) | 중단 허용되는 배치/학습 |
| 전용 | 필요시 약정 | 없음 | 낮음 | 규정/라이선스 요구사항 |

## 보안 그룹 (Security Group)

> **정의:** EC2 인스턴스를 보호하는 **가상의 방화벽**

> **비유:** 아파트 경비실처럼, 누가 들어오고 나갈 수 있는지를 통제합니다.  
> "택배 기사는 1층 로비까지만, 거주자는 자기 층까지만" 같은 방식으로요.

---

### 포트 제어 방식

**기본 정책: 모두 막고, 필요한 것만 허용**

```
기본 상태: 모든 인바운드 트래픽 차단 ❌

허용 규칙 추가:
- 80/443 포트 (웹 트래픽): 전체 허용 ✅
- 22 포트 (SSH): 내 IP만 허용 ✅
- 3306 포트 (MySQL): 특정 서버 IP만 허용 ✅
```

**중요 특징:**

| 특징 | 내용 |
|---|---|
| **허용(Allow)만 가능** | 거부(Deny) 규칙을 직접 만들 수 없음 |
| **Stateful** | 인바운드 허용 시 해당 연결의 아웃바운드는 자동 허용 |
| **인스턴스 단위 적용** | 서브넷 전체가 아닌 개별 인스턴스에 적용 |

---

### 적용 단위 — 인스턴스 레벨

보안 그룹은 **서브넷 단위가 아닌 인스턴스 단위**로 적용됩니다.

```
같은 서브넷 내 두 인스턴스:
- 인스턴스 A: 보안그룹 Web (80, 443 허용)
- 인스턴스 B: 보안그룹 DB (3306만 허용)
→ 완전히 다른 보안 정책 적용 가능 ✅
```

---

### 다중 보안 그룹 적용

하나의 인스턴스에 **여러 개의 보안 그룹을 동시에 설정** 가능합니다.  
이 경우 부착된 모든 보안 그룹의 **허용 규칙을 합산**하여 트래픽을 통과시킵니다.

```
인스턴스에 보안그룹 A + 보안그룹 B 동시 적용:

보안그룹 A: 80 포트 허용
보안그룹 B: 443 포트 허용

결과: 80, 443 포트 모두 허용 ✅ (합집합)
```

---

### 주요 포트 참고표

| 서비스 | 프로토콜 | 포트 |
|---|---|---|
| HTTP | TCP | 80 |
| HTTPS | TCP | 443 |
| SSH (Linux 원격접속) | TCP | 22 |
| RDP (Windows 원격접속) | TCP | 3389 |
| MySQL / Aurora | TCP | 3306 |
| PostgreSQL | TCP | 5432 |
