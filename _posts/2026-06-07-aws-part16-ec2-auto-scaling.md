앞서 배운 '수평 확장(Scale Out)'과 '탄력성(Elasticity)'을 실제로 구현해 주는 핵심 서비스인  
**EC2 Auto Scaling**의 구성 요소와 스케일링 정책을 정리합니다.

---

## AWS Auto Scaling 개요

애플리케이션을 모니터링하여 서버 용량을 **자동으로 조정**해 주는 서비스입니다.  
가장 저렴한 비용으로 안정적이고 예측 가능한 성능을 유지하는 것이 핵심 목표입니다.

> **비유:** 항공사의 자동 운항 편수 관리 시스템입니다.  
> 예약률이 치솟으면 임시편을 자동으로 투입하고, 비수기엔 빈 기체를 격납고로 돌립니다.  
> 운항 담당자가 24시간 모니터링하지 않아도, 시스템이 알아서 적정 편수를 맞춰줍니다.

EC2 외에도 DynamoDB, Aurora, ECS, Spot Fleet 등 다양한 AWS 서비스의 규모 조정에 사용됩니다.

---

## EC2 Auto Scaling의 주요 목적

### 정확한 인스턴스 수 보장

사용자가 설정한 **최소(Min) / 최대(Max) / 원하는(Desired)** 인스턴스 숫자 범위를 항상 유지합니다.

```
Min: 2대 / Desired: 4대 / Max: 10대

트래픽 급증 → CPU 80% 초과 → Scale-Out → 10대까지 자동 추가
트래픽 감소 → CPU 20% 이하 → Scale-In  → 2대까지 자동 축소
인스턴스 장애 → Health Check 실패 → 자동 교체 (최소 2대 유지)
```

### 다양한 스케일링 정책 지원

- **동적 크기 조정:** CPU 부하 등 실시간 지표에 따라 유동적으로 인스턴스를 늘립니다.
- **예약된 크기 조정:** 특정 시간에 미리 인스턴스 개수를 늘려둡니다.
- **예측 기반 크기 조정:** 머신러닝으로 미래 트래픽을 예측하여 사전 준비합니다.

### 고가용성 확보

여러 가용 영역(AZ)에 인스턴스가 골고루 분산되도록 자동으로 배치합니다.

## EC2 Auto Scaling의 3가지 핵심 구성 요소

Auto Scaling이 동작하려면 **무엇을, 언제, 얼마나** 실행할지 정의해야 합니다.

### 1. 시작 템플릿 (Launch Template) — "무엇을 실행할 것인가?"

새로 찍어낼 EC2의 '설계도'입니다.

> **비유:** 항공사의 기체 도입 표준 사양서입니다.  
> "엔진은 몇 호, 좌석 배치는 이렇게, 기내 소프트웨어는 이 버전으로" 정해두면  
> 이 사양서(Launch Template)대로 새 기체(EC2)를 언제든 동일하게 찍어낼 수 있습니다.  
> 사양서를 업데이트하면, 이후 도입하는 기체는 모두 새 규격으로 나옵니다.

| 설정 항목 | 내용 |
|---|---|
| AMI | 인스턴스에 설치할 운영체제 이미지 |
| 인스턴스 타입 | t3.medium, c5.xlarge 등 사양 |
| 보안 그룹 | 허용할 네트워크 규칙 |
| 키 페어 | SSH 접속용 키 |
| IAM 역할 | 인스턴스에 부여할 권한 |
| User Data | 최초 실행 시 자동 실행할 스크립트 |

> **Launch Configuration(시작 구성)** 은 구형 방식으로 현재는 Launch Template 사용을 권장합니다.

### 2. 모니터링 및 상태 확인 — "언제 실행시킬 것인가?"

CloudWatch(모니터링)나 ELB(로드밸런서)와 연계하여 타이밍을 결정합니다.

```
예시 1: CloudWatch 경보
  "CPU 사용률이 70%를 5분간 초과하면 인스턴스 2대 추가"

예시 2: ELB Health Check 연동
  "응답이 없는 인스턴스가 있으면 해당 인스턴스를 교체"
```

### 3. 설정 — "얼마나 실행시킬 것인가?"

Auto Scaling 그룹(ASG) 내에서 유지할 인스턴스 개수를 설정합니다.

> **비유:** 항공사의 일일 운항 편수 기준입니다.  
> "이 노선은 **최소** 2편(새벽·심야 기본편)은 반드시 운항해야 하고,  
> **평시**엔 5편이면 충분하며, **최대** 20편 이상은 슬롯(공항 이착륙 허가)이 없어 불가하다."  
> Desired는 현재 목표 편수, 예약률에 따라 Auto Scaling이 Min~Max 사이에서 자동 조절합니다.

| 설정값 | 설명 |
|---|---|
| **Min (최솟값)** | 항상 유지해야 하는 최소 인스턴스 수 |
| **Max (최댓값)** | 비용 폭발 방지를 위한 최대 인스턴스 수 |
| **Desired (원하는 용량)** | 현재 목표로 삼는 인스턴스 수 (Min~Max 사이) |

## 종료 정책 (Termination Policy)

Scale-In(인스턴스 축소) 시 **어떤 인스턴스를 먼저 종료할 것인가**를 결정합니다.

> **비유:** 감편 시 어떤 기체부터 격납고로 돌릴지 정하는 기준입니다.  
> 기본적으로는 "기체가 한쪽 공항에 치우쳐 있으면 그쪽부터 → 구형 사양서로 도입된 기체 → 다음 과금 시간이 가장 가까운 기체" 순서로 회항시켜  
> 공항 간 균형을 맞추고, 최신 사양서(새 템플릿)의 기체는 최대한 남깁니다.

### 기본 정책 (Default) — 순서

1. **인스턴스가 가장 많이 몰린 AZ** 를 먼저 타겟으로 삼습니다. (AZ 간 균형 유지)
2. 그중에서 **가장 오래된 시작 템플릿**으로 만들어진 구형 인스턴스를 종료합니다.
3. 템플릿이 동일하다면 **다음 과금 시간(Billing Hour)에 가장 가까운 인스턴스**를 종료하여 비용을 절약합니다.

### 커스텀 정책

| 정책 | 설명 |
|---|---|
| OldestInstance | 가장 오래된 인스턴스부터 종료 |
| NewestInstance | 가장 최근에 만들어진 인스턴스부터 종료 |
| OldestLaunchTemplate | 가장 오래된 템플릿으로 만든 인스턴스부터 종료 |
| Lambda 기반 커스텀 | 복잡한 자체 종료 로직 적용 가능 |

## 4가지 스케일링 정책

### 1. 수동 스케일 (Manual Scaling)

관리자가 직접 인스턴스 숫자(Min/Max/Desired)를 조절합니다.

- 주로 **개발 환경** 이나 자동 정책 적용 전 **사전 테스트** 용도로 활용
- 수동 조절 시 다른 스케일링 정책을 비활성화하는 것이 좋음

### 2. 스케줄 기반 스케일링 (Scheduled Scaling)

트래픽 변동 시점을 미리 예측할 수 있을 때, **특정 시간과 날짜를 지정**하여 인스턴스 수를 증감합니다.

```
예시: 매주 수요일 오후 6시 → 인스턴스 10대로 증가 (게임 정기 업데이트 대비)
예시: 매일 새벽 2시 → 인스턴스 20대로 증가 (배치 데이터 처리 작업)
예시: 블랙프라이데이 전날 오전 9시 → 인스턴스 50대로 미리 증가
```

한 번만 실행하거나, 매일/매주 반복 실행하도록 설정할 수 있습니다.

### 3. 동적 스케일 (Dynamic Scaling)

특정 지표 기준치에 도달했을 때 **실시간으로 반응**하여 인스턴스를 늘리거나 줄입니다.  
가장 일반적으로 많이 쓰이는 자동화 방식입니다.

> **비유:** 예약 현황판을 실시간으로 보며 임시편을 투입하는 방식입니다.  
> 예약률이 90%를 넘으면 즉시 임시편을 띄우고, 50% 아래로 떨어지면 편수를 줄입니다.  
> 운항 담당자가 직접 판단하지 않아도, 예약률 수치에 따라 시스템이 자동으로 반응합니다.

**작동 원리:**

```
CloudWatch 지표 감시
  → 기준치 초과 시 CloudWatch Alarm 발동
  → Auto Scaling 정책 실행 (Scale-Out / Scale-In)
```

**대표적인 정책 유형:**

| 유형 | 설명 |
|---|---|
| **Target Tracking (타겟 추적)** | "CPU 사용률을 60%로 유지해라" 처럼 목표값을 설정하면 자동 조정 |
| **Step Scaling (단계별)** | 기준치 초과 정도에 따라 단계별로 다른 수의 인스턴스 추가 |
| **Simple Scaling** | 알람 발동 시 고정된 수의 인스턴스를 추가/제거 |

### 4. 예측 기반 스케일 (Predictive Scaling)

머신러닝을 활용해 **과거 사용 패턴을 분석하고 향후 수요를 예측**하여, 부하 발생 '전에' 미리 인스턴스를 준비합니다.

> **비유:** 항공사가 작년 여름 성수기 예약 패턴을 분석해 올해 여름 증편을 미리 확정하는 방식입니다.  
> 동적 스케일링이 "지금 예약이 꽉 찼다, 당장 임시편 투입!"이라면,  
> 예측 기반 스케일링은 "작년에도 7월 마지막 주가 피크였으니, 올해도 그 주 전에 미리 기체를 준비해 두자"입니다.  
> 기체가 취항 준비를 마치는 데 시간이 걸리기 때문에, 트래픽이 몰린 후 대응하면 이미 늦습니다.

**작동 원리:**

```
과거 14일간 CloudWatch 지표 분석
  → 트래픽 패턴 학습 (매일 오후 2시 급증 패턴 발견)
  → 향후 48시간 수요 예측
  → 예측된 시간 전에 미리 인스턴스 추가
```

**적합한 서비스:**

- 반복되는 트래픽 패턴이 명확한 경우
- 인스턴스 부팅 및 설정 시간이 길어서 트래픽 급증 후 대응하면 늦는 서비스

**비교:**

| 정책 | 언제 반응 | 특징 |
|---|---|---|
| 동적 스케일 | 트래픽 급증 **후** | 실시간 대응, 즉각적 |
| 예측 기반 스케일 | 트래픽 급증 **전** | 선제적 대응, 패턴 학습 필요 |

> 두 정책을 함께 사용하면 예측이 빗나간 경우에도 동적 스케일이 보완해 줍니다.
