클라우드 보안의 핵심이자 뼈대인 IAM 파트입니다.  
사내에서 업무 프로세스를 표준화하거나 문서 접근 권한을 나눌 때 체계적인 관리가 필수적이듯,  
AWS 인프라 전체의 접근 권한을 안전하게 통제하는 수문장 역할을 하는 것이 바로 **IAM**입니다.

---

## IAM(Identity and Access Management)이란?

> **정의:** AWS 서비스와 리소스에 대한 접근 권한을 안전하게 제어하고 관리하는 **글로벌 서비스**

> **한 줄 비유:** AWS라는 거대한 건물의 **출입증 발급 및 보안 시스템**입니다.  
> 누가 어느 방에 들어갈 수 있는지, 무엇을 할 수 있는지를 모두 IAM이 결정합니다.

**주요 기능:**

| 기능 | 설명 |
|---|---|
| 사용자 생성 및 관리 | AWS를 사용할 계정을 만들고 관리 |
| 패스워드 정책 관리 | 비밀번호 규칙 설정 (최소 길이, 특수문자 필수 등) |
| MFA(다중 인증) 설정 | 비밀번호 + 추가 인증 수단으로 보안 강화 |
| 임시 권한 부여 | 특정 작업에만 잠깐 쓰는 권한 발급 |
| 다른 계정과 리소스 공유 | Cross-Account 접근 허용 |

## IAM을 구성하는 4가지 핵심 요소

> **전체 비유:** 회사 출입증 시스템으로 이해하면 쉽습니다.

### ① 사용자 (User)

> **비유:** 갓 입사해서 아직 아무 방도 못 들어가는 **신입 사원**입니다.

- AWS를 사용하는 **사람** 또는 **애플리케이션(시스템)** 을 나타내는 계정
- 생성 직후에는 **아무 권한도 없음** → 정책이나 그룹을 통해 권한을 부여받아야 함
- 사람뿐 아니라 특정 프로그램이나 서비스도 IAM User로 만들어서 권한을 줄 수 있음

```
신입 사원 입사
→ 아무 방도 못 들어감
→ 인사팀에서 출입증(정책)을 발급해줘야 이동 가능
```

### ② 그룹 (Group)

> **비유:** 회사의 **부서(팀)** 입니다.  
> 개발팀 전체에 서버실 출입 권한을 주면, 팀원 모두가 자동으로 서버실에 들어갈 수 있게 됩니다.

- 여러 사용자를 묶는 단위
- 그룹에 정책(권한)을 부여하면 → **그룹에 속한 모든 사용자에게 동일한 권한이 일괄 적용**
- 사람이 늘거나 줄어도, 그룹 권한만 관리하면 되므로 효율적

```
개발팀 그룹 → EC2 접근 권한 부여
→ 개발팀 소속 사용자 전원이 EC2 사용 가능

신규 개발자 입사 → 개발팀 그룹에 추가
→ 따로 권한 설정 없이 자동으로 EC2 사용 가능 ✅
```

> **주의:** 그룹 안에 그룹을 넣는 중첩은 불가능합니다.

### ③ 정책 (Policy)

> **비유:** 사원증에 새겨진 **출입 인가 코드(보안 등급)** 입니다.  
> "이 사람은 3층 서버실 출입 가능, 5층 임원실 출입 불가"처럼 구체적인 규칙이 적혀있습니다.

- 사용자·그룹·역할이 **"무엇을 할 수 있는지"** 정의한 권한 문서
- **JSON 형식**으로 작성됨

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::my-bucket/*"
    }
  ]
}
```

**정책의 4가지 구성 요소:**

| 요소 | 설명 | 예시 |
|---|---|---|
| **Effect** | 허용(Allow) 또는 거부(Deny) | `"Effect": "Allow"` |
| **Action** | 허용/거부할 동작 | `"s3:GetObject"` (S3에서 파일 읽기) |
| **Resource** | 대상 리소스 (ARN) | `"arn:aws:s3:::my-bucket/*"` |
| **Condition** | 적용 조건 (선택) | 특정 IP에서만 허용 등 |

> **💡 중요 원칙 — 명시적 거부 우선:**  
> Allow와 Deny가 동시에 적용되면 **항상 Deny가 이깁니다.**  
> "들어오세요"와 "들어오지 마세요"가 동시에 붙어 있으면, 못 들어가는 것과 같습니다.

### ④ 역할 (Role)

> **비유:** 필요할 때만 잠깐 쓰는 **완장** 또는 **임시 마스터키**입니다.  
> 평소에는 일반 사원이지만, 소방 안전 관리자 완장을 차면 소방 시설에 접근할 수 있게 됩니다.  
> 완장을 반납하면 다시 일반 사원으로 돌아갑니다.

- 특정 사용자에게 **영구적으로 묶이지 않은** 권한의 집합
- IAM 사용자뿐만 아니라 **EC2 같은 AWS 서비스**도 역할을 부여받아 다른 서비스에 접근 가능
- 권한이 **일시적**으로 부여됨 (Temporary Security Credentials)

**역할의 주요 사용 사례:**

| 상황 | 설명 |
|---|---|
| EC2 → S3 접근 | EC2 인스턴스에 S3 읽기 역할을 부여 → 코드에 키를 하드코딩할 필요 없음 |
| 다른 AWS 계정 접근 | A 계정 사용자가 B 계정 리소스를 잠깐 사용해야 할 때 |
| 외부 서비스 연동 | GitHub Actions 등 외부 CI/CD 도구가 AWS에 배포할 때 |

```
[역할 없이]
EC2 코드 안에 AWS Access Key를 직접 입력 → 키 유출 위험 ❌

[역할 사용]
EC2에 "S3 읽기 역할" 부여 → 코드에 키 없이 자동으로 S3 접근 ✅
```

## Root 사용자 vs IAM 사용자

> **비유:**  
> Root = 회사의 **대표이사** (모든 결재권 보유, 해고도 가능)  
> IAM = **일반 직원** (담당 업무 범위 내에서만 권한 행사)

| 구분 | Root 사용자 | IAM 사용자 |
|---|---|---|
| 생성 시점 | AWS 계정 생성 시 자동 생성 | 관리자가 직접 생성 |
| 권한 범위 | 모든 권한 (제한 불가) | 정책으로 세밀하게 제한 가능 |
| 탈취 시 위험도 | 매우 높음 (복구 어려움) | 상대적으로 낮음 |
| 일상 업무 사용 | ❌ 절대 금지 | ✅ 권장 |

**Root 사용자만 할 수 있는 작업:**
- AWS 계정 설정 변경
- 요금 및 결제 설정
- Support Plan 변경
- **계정 삭제**

> **⚠️ 보안 필수 수칙:**
> 1. Root 사용자는 **MFA(다중 인증)** 반드시 설정
> 2. Root 사용자 Access Key는 **절대 생성하지 말 것**
> 3. 평소 모든 작업은 **IAM 사용자**로 진행

## 권한 검증 과정

사용자가 EC2를 사용하려 할 때 AWS가 권한을 확인하는 순서입니다.

```
① 사용자 본인에게 직접 EC2 정책이 있는가?
        ↓ 없으면
② 사용자가 속한 그룹에 EC2 정책이 있는가?
        ↓ 없으면
③ 접근 거부 (Access Denied)
```

**서비스 간 접근 (예: EC2 → S3):**

```
EC2가 S3에 접근하려 할 때
→ EC2에 S3 접근 권한이 있는 '역할(Role)'이 부여되어 있는가?
→ 있으면 허용 ✅ / 없으면 거부 ❌
```

> **중학생 비유로 전체 흐름 정리:**  
> 학교 도서관(AWS)에서 책(리소스)을 빌리려고 합니다.  
> ① 내 학생증(사용자 정책)에 도서관 이용 권한이 있나?  
> ② 내가 속한 학생회(그룹 정책)에 도서관 이용 권한이 있나?  
> ③ 둘 다 없으면 → 사서 선생님이 "넌 안 돼" (Access Denied)

## 최소 권한의 원칙 (Least Privilege)

> IAM의 핵심 보안 원칙: **꼭 필요한 권한만, 필요한 만큼만 부여한다.**

> **비유:** 청소부 아저씨에게 건물 마스터키를 줄 필요는 없습니다.  
> 청소할 구역의 열쇠만 주면 충분합니다.

모든 사용자와 서비스에 관리자 권한(AdministratorAccess)을 주면 편하지만, 계정 하나가 탈취되면 전체가 위험해집니다.  
처음엔 최소한의 권한만 주고, 필요할 때 하나씩 추가하는 방식이 안전합니다.
