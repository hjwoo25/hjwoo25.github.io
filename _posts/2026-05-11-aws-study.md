# AWS & Network 기초 스터디 노트

## ☁️ Part 1. AWS 기초 및 핵심 서비스

### 1. AWS를 배워야 하는 이유
* **압도적인 점유율:** 대한민국 및 글로벌 기준 점유율 1위 클라우드 프로바이더.
* **풍부한 생태계:** 사용자가 많아 레퍼런스, 커뮤니티, 트러블슈팅 리소스가 방대함.
* **지속적인 발전:** 다양한 서비스 제공 및 지속적인 업데이트.

### 2. AWS 서비스 공부 순서 및 팁
* AWS 서비스들은 긴밀하게 연결되어 있어 하나의 서비스만 독립적으로 완벽히 이해하기 어려움.
* 한 서비스를 적절히 학습한 뒤 다른 서비스를 보고 **다시 돌아와서 복습하는 방식**을 추천.
* **필수 학습 서비스:** `EC2`, `IAM`
* **연계 학습 서비스:**
  * EC2 연계: `EBS`, `ELB`, `Auto Scaling`, `Budgets`
  * 인프라 및 데이터: `VPC`, `S3`, `RDS`, `Aurora`

### 3. 핵심 서비스 요약
* **클라우드 컴퓨팅:** 컴퓨팅 파워를 빌려 쓰는 것.
* **EC2 (Elastic Compute Cloud):** 컴퓨팅 파워(서버)를 빌려 쓰는 대표적인 서비스.
* **IAM (Identity and Access Management):** AWS의 글로벌 보안 및 관리 서비스.
  * *기능:* AWS 계정 관리, 리소스 및 사용자 권한 제어.
* **VPC (Virtual Private Cloud):** 클라우드 내에 생성하는 가상의 데이터센터.
  * 원하는 대로 사설망 구축 및 서브넷 구성 가능.
  * `EC2`, `RDS`, `Lambda` 등이 실행되는 격리된 공간.
  * 보안 설정 (IP Block, 외부 인터넷에 노출되지 않는 프라이빗 EC2 구성 등).
* **S3 (Simple Storage Service):** 무제한 용량을 제공하는 객체 스토리지 (웹하드와 유사).
  * 99.999999999%(11 나인)의 내구성(파일을 잃어버리지 않을 능력) 제공.
  * *가용성(원할 때 언제든 접근할 수 있는 능력)과는 다른 개념.*
* **RDS (Relational Database Service):** 관계형 데이터베이스를 제공하는 관리형 서비스.
  * 암호화 및 자동 백업 지원.

## 🌐 Part 2. 네트워크 기초 (OSI 7 Layer)

> **암기 팁:** **P**lease **D**o **N**ot **T**hrow **S**ausage **P**izza **A**way
> (Physical - Data Link - Network - Transport - Session - Presentation - Application)
> *최근에는 실무적으로 TCP/IP 4계층(Network Access - Network - Transport - Application) 모델을 주로 사용함.*

### Layer 1~4: 하드웨어 및 전송 기반

* **Layer 1. Physical Layer (물리 계층)**
  * 장치를 연결하기 위한 물리적 매체(전압, 케이블, 안테나 규격 등) 정의.
  * *단위:* Bits
  * *장비:* 허브 (데이터를 단순히 브로드캐스팅하는 '확성기' 역할. 충돌 방지 기능 없음).

* **Layer 2. Data Link Layer (데이터 링크 계층)**
  * 물리적 통신을 제어하여 디바이스 간 통신을 안정화하고 충돌을 방지함.
  * *단위:* Frame
  * *장비:* 스위치 (Switch) - 내부에 MAC 주소 테이블을 가지고 있어 각 포트별 디바이스를 독립적으로 관리하고 충돌을 방지함.
  * *MAC Address:* 네트워크 인터페이스(NIC)에 부여된 고유 식별자 (48 bits). 변하지 않는 고유값(주민등록번호와 유사).
  * *한계:* 로컬 네트워크 내 통신은 가능하나, 외부 네트워크와의 통신은 불가함.

* **Layer 3. Network Layer (네트워크 계층)** 
  * 여러 노드의 경로를 찾아(라우팅) 서로 떨어진 로컬 네트워크 간의 통신을 지원하고 데이터가 올바르게 전달될 수 있도록 하는 계층.
  * *단위:* Packet (패킷)
  * *장비:* 라우터 (Router)

  * **IP Address (인터넷 프로토콜 주소):**
    * 통신 주체를 식별하기 위한 논리적 아이디. MAC 주소와 달리 수시로 변동될 수 있음.
    * `IPv4`: 32bits. 주소 고갈을 막기 위해 공인/사설 IP로 구분하여 사용.
    * `IPv6`: 128bits. 사설 IP 개념이 불필요할 만큼 방대한 주소를 제공.

  * **CIDR Notation (IP 주소의 집합 표현):** 
    * 다양한 IP 주소를 통틀어서 표현하는 표기법. (네트워크 주소 + 호스트 주소)
    * 형식: `A.B.C.D/E` (예: 192.168.2.0/24)
    * `/24`는 전체 32비트 중 앞의 24비트가 네트워크를 식별하는 데 사용된다는 뜻. 
    * 나머지는 호스트 주소(32 - 24 = 8비트). 즉, $2^8$(256)개의 IP 주소를 해당 네트워크 망에서 보유 가능.

  * **Subnet Mask (서브넷 마스크):**
    * IP 주소에서 어디까지가 네트워크 비트이고, 어디부터가 호스트 비트인지 구분해 주는 역할.
    * `AND 연산`(둘 다 1일 때만 1)을 활용하여 네트워크 주소만 필터링함. 
    * (예: IP가 192.168.2.122 이고 서브넷 마스크가 255.255.255.0 일 때, 이를 바탕으로 같은 네트워크 대역인지 파악).

  * **Router (라우터):**
    * 네트워크 간의 패킷을 주고받는 Layer 3 핵심 장치.
    * IP 대역별 최적 경로(라우팅 테이블)를 수집하고 관리함.
    * 목적지 IP가 내부 로컬 네트워크가 아니라면 패킷을 라우터로 전달 -> 라우터는 프레임에 넣어 최적 경로의 다음 라우터로 전달.

  * **ARP (Address Resolution Protocol):** 
    * 논리적 주소인 IP를 통해 물리적 주소인 MAC Address를 알아내는 프로토콜.
    * 브로드캐스트(Broadcast) 방식으로 네트워크에 "이 IP 가진 사람 MAC 주소 뭐야?"라고 요청하고, 응답받은 MAC 주소를 확정하여 ARP 테이블에 저장.

  * **💡 전체 흐름: 라우터까지 데이터가 전달되는 과정**
    1. 대상 IP가 로컬인지 외부인지 식별 (서브넷 마스크 활용).
    2. 네트워크 주소가 다르다면(외부라면) 패킷을 라우터로 보내야 함.
    3. 라우터의 IP는 알지만 MAC 주소를 모를 때 `ARP`를 실행.
    4. ARP를 통해 알아낸 라우터의 MAC 주소로 프레임을 생성하여 데이터 전달.

  * **한계 (해결하지 못한 문제):**
    * 한 번에 하나의 통신만 가능하여 여러 앱이 동시에 통신할 수 없음.
    * 패킷의 순서가 보장되지 않고, 유실에 대한 대응이 불가능함. (이 문제는 다음 계층인 Layer 4 전송 계층의 TCP가 해결함!)
* **Layer 4. Transport Layer (전송 계층)**
  * 통신 주체끼리 데이터 전달의 신뢰성을 확보.
  * *단위:* Segment (세그먼트)
  * **TCP (Transmission Control Protocol):**
    * 연결 지향적. 지속적인 채널 수립으로 패킷 순서와 무결성을 보장 (비교적 느림).
    * *TCP 3-way Handshake:* 통신 수립 과정 (`SYN` -> `SYN-ACK` -> `ACK`).
    * *사용처:* 웹(HTTP/HTTPS), 이메일, 파일 전송 등 신뢰성이 중요한 곳.
  * **UDP (User Datagram Protocol):**
    * 비연결형 (Connectionless). 무결성, 순서를 체크하지 않음. 패킷 유실 가능성이 있으나 빠름.
    * *사용처:* 스트리밍, 온라인 게임, DNS(UDP 53) 등 속도가 중요한 곳.
  * **Port (포트):**
    * IP 통신 위에서 올바른 프로세스(어플리케이션)를 찾아가기 위한 논리적 단위.
    * *Well Known Port:* HTTP(80), HTTPS(443), SSH(22), MySQL(3306) 등.
    * *Ephemeral Port:* 클라이언트 연결 시 임의로 지정되는 포트.

### Layer 5~7: 소프트웨어 및 어플리케이션 영역

* **Layer 5. Session Layer (세션 계층)**
  * 통신 주체 간의 연결(세션)을 유지하고 관리하는 방법 정의. (예: HTTP Cookie).
* **Layer 6. Presentation Layer (표현 계층)**
  * 받은 데이터를 해석하고 포맷팅하는 방법 정의 (인코딩, 암호화 등).
* **Layer 7. Application Layer (어플리케이션 계층)**

## 🌍 Part 3. DNS (Domain Name System) 기초

### 1. DNS란?
* 우리가 인터넷을 사용할 때, 사람이 읽기 편한 **도메인 이름(예: google.com)**을 머신이 통신할 수 있는 **IP 주소**로 변환해 주는 시스템.
* 전 세계적인 시스템이며 **ICANN**(국제 인터넷 주소 관리 기구)에서 총괄 관리함.

### 2. 도메인 및 레코드 주요 용어
* **도메인 (Domain):** 대상의 IP 주소 등의 정보와 매핑되는, 사람이 알아볼 수 있는 문자열.
* **서브도메인 (Subdomain):** 도메인 중 앞에 추가 문자열이 붙은 형태 (예: `text.example.com`).
* **APEX 도메인 (Root Domain):** 앞에 추가 문자열이 없는 순수한 최상위 도메인 (예: `example.com`).
* **레코드 (Record):** 도메인이 어떤 데이터와 매칭되는지 정의한 기록.
  * `A 레코드`: IPv4 주소와 매핑.
  * `MX 레코드`: 메일 서버와 매핑.
* **도메인 존 (Domain Zone) & 존 파일 (Zone File):** 도메인의 정보를 담은 레코드들의 집합과 이를 저장한 텍스트 파일.
* **DNS 쿼리 (Query):** 주어진 도메인에 해당하는 정보를 요청하는 질의.

### 3. DNS 서버의 종류
* **DNS Resolver (리졸버):** 
  * 사용자와 NS 서버 사이에 위치하여, 유저의 요청을 받아 IP 주소를 대신 '탐문 수색'해 오는 서버. (보통 통신사 ISP가 관리)
* **네임 서버 (NS, Name Server):** 
  * DNS 쿼리를 존 파일 기반으로 응답해 주는 서버.
  * *Authoritative:* DNS 정보의 원본(존 파일)을 직접 가지고 있는 최종 결정권자 서버.
  * *Non-authoritative:* 다른 서버를 조회한 뒤 정보를 임시로 보관(캐시)하고 응답하는 서버.

### 4. DNS의 계층 구조와 동작 원리 (IP 탐문 수색 과정)
전 세계의 방대한 DNS 쿼리를 감당하기 위해 **[Root -> TLD -> Domain(NS) -> Subdomain]** 순서의 계층 구조를 가짐.

1. **DNS Root (루트 서버):**
   * 리졸버가 DNS 쿼리 시 최초로 찾아가는 거점. IANA에서 조율하는 13개(A~M)의 관리 주체가 운영함.
   * *Root Hints File:* DNS Root의 주소를 담은 파일로 리졸버에 하드코딩 되어 있음.
   * 💡 *Resolver:* "`.kr`로 끝나는 도메인은 어디서 물어봐야 해?" -> *Root:* "TLD 관리자 주소 알려줄게."
2. **TLD (Top Level Domain):**
   * 실질적으로 정보를 가지고 있는 최상위 레벨 (`.com`, `.org`, `.net`, `.kr` 등).
   * 국가 코드(ccTLD)나 스폰서/일반 도메인(gTLD) 등으로 나뉘며, 각 TLD Registry(예: KISA, Verisign)가 관리함.
   * 💡 *Resolver:* "KISA야, `test.kr` 도메인은 누가 관리해?" -> *TLD:* "해당 도메인의 담당 NS 서버 주소는 여기야."
3. **NS 서버 (Name Server):**
   * 해당 도메인 및 서브도메인이 어떤 IP와 매핑되는지(레코드) 기록된 최종 존 파일을 보유한 곳.
   * 💡 *Resolver:* "담당 NS 서버야, `lecture.test.kr`의 IP가 뭐니?" -> *NS:* "최종 매핑된 IP 주소는 192.0.2.1 이야!" (탐문 종료)

### 5. 도메인 등록 방법
* **도메인 등록 대행 (Registrar):** ICANN의 인증을 받고 TLD Registry와 협의하여 도메인을 대신 등록해 주는 주체. (예: 가비아, GoDaddy, Cafe24, **AWS Route 53**)
* 등록 시 TLD Registry의 남은 슬롯에 자신이 운영할 'NS 서버 주소'를 예치하듯 등록함.
* NS 서버는 직접 개인 서버를 구축해 사용하거나, 가비아 및 **AWS Route 53** 같은 DNS 호스팅 서비스 업체에서 대여하여 사용 가능함.

## 🚀 Part 4. 캐싱 (Caching) 기초

### 1. 캐싱(Caching)이란?
* 데이터의 복제본이나 복잡한 연산 결과를 임시로 저장하여, 이후 동일한 요청이 올 때 응답을 효율적이고 빠르게 처리하는 기술.
* **목적:** 자주 찾는 데이터나 무거운 연산 결과를 매번 다시 계산/조회하지 않고 효율적으로 전달하기 위함.

### 2. 장단점
* **장점 (Pros):**
  * 요청에 대해 매우 빠르게 데이터를 전달할 수 있음.
  * 서버나 데이터베이스(원본)의 복잡한 연산 리소스 및 부하를 크게 줄일 수 있음.
* **단점 (Cons):**
  * 원본 데이터와 캐시 데이터 간의 **일관성(Consistency)** 유지가 어려움.
  * 시스템 아키텍처의 복잡도가 증가함.
  * 캐시 저장소(주로 메모리) 사용에 따른 추가 인프라 비용 발생.

### 3. 주요 개념
* **원본 (Origin):** 캐싱할 데이터나 연산 결과를 제공하는 본래의 주체 (예: DB, 메인 서버).
* **캐시 히트 (Cache Hit):** 요청한 데이터가 캐시에 존재하여, 원본에 묻지 않고 캐시에서 바로 응답할 수 있는 (지향해야 할) 성공적인 상황.
* **캐시 미스 (Cache Miss):** 요청한 데이터가 캐시에 없어, 결국 별도로 원본에 요청을 보내 응답을 받아와야 하는 상황.
* **캐시 만료 (Cache Eviction):** 공간 확보나 최신화를 위해 캐시에 있는 데이터를 삭제하는 행위.
* **TTL (Time To Live):** 캐시 데이터가 얼마만큼 살아있는지를 나타내는 유효 시간 단위.

### 4. 캐싱 쓰기/읽기 전략 (Caching Strategies)
캐시에 원본 데이터를 언제, 어떻게 채울 것인가에 대한 정책입니다.

* **Lazy Loading (지연 로딩):** 
  * 데이터 요청이 있을 때만 캐시에 원본 데이터를 적재.
  * 불필요한 데이터가 캐싱되지 않으나, 최초 데이터 요청 시에는 캐시 미스가 발생하여 로딩(지연)이 필요함.
* **Eager Loading (즉시 로딩):** 
  * 미리 캐시에 데이터를 다 채워두고 요청을 기다리는 정책.
  * 데이터가 항상 준비되어 있어 빠르지만, 모든 데이터를 채우기에 불필요한 캐시 용량이 낭비될 수 있고 최초 로딩에 매우 큰 리소스가 필요함.
* **Write-Through (동시 쓰기):** 
  * 데이터가 변경되거나 저장되는 시점에 원본과 캐시에 **동시에** 저장.
  * 데이터의 일관성이 항상 완벽하게 보장되지만, 두 곳에 모두 써야 하므로 쓰기 과정이 복잡해지고 느려질 수 있음.
* **Write-Back (지연 쓰기):** 
  * 데이터를 캐시에만 먼저 빠르게 쓰고, 나중에 원본에 업데이트.
  * 쓰기가 빠르고 간단하지만, 원본에 데이터가 도달하기 전에 캐시 서버에 문제가 생기면 데이터가 유실될 가능성이 있음.

### 5. 캐시 만료 정책 (Eviction Policies)
캐시 공간이 부족할 때 어떤 데이터를 먼저 지울 것인가에 대한 정책입니다.

* **TTL (Time to Live):** 일정 시간이 지나면 무조건 만료. 항상 갱신되므로 최신성은 보장되나, 계속 사용 중인 데이터도 무조건 다시 갱신해야 함.
* **LRU (Least Recently Used):** 사용된 시점이 가장 오래된(먼) 데이터부터 만료. 최근 사용 패턴을 반영하기 좋으나, 특정 상황에서는 비효율적일 수 있음.
* **LFU (Least Frequently Used):** 가장 덜(적게) 사용된 데이터부터 만료. 자주 사용되는 데이터를 안정적으로 남길 수 있으나, 과거에만 반짝 쓰이고 현재는 안 쓰이는 데이터가 자리를 차지할 수 있음.
* **FIFO (First In First Out):** 가장 먼저 들어온 데이터부터 만료. 구현이 간단하지만, 데이터의 사용 패턴을 전혀 고려하지 않아 비효율적임.

### 6. 주요 사용 예시 (Use Cases)
* **CDN (Content Delivery Network):** 전 세계 사용자에게 이미지, 영상 등 정적 리소스를 빠르게 전달.
* **ElastiCache (Redis / Memcached):** AWS에서 제공하는 인메모리 캐시. (랭킹 보드, 로그인 세션 데이터 등에 주로 사용)
* **웹 브라우저 (Web Browser):** 사용자 PC에 이미지 등을 캐싱하여 다음 접속 시 렌더링 속도 향상.
* **RAM (메모리):** 하드디스크와 CPU 사이에서 속도 차이를 극복하는 하드웨어적 캐시 역할.
  * 사용자가 직접 맞닿는 데이터를 어떻게 처리할지 정의.
  * *예시:* HTTP 프로토콜 (Method, Status code, Header 등).
  * *참고:* AWS의 ALB(Application Load Balancer)는 이 L7 계층에서 작동하며, HTTP 헤더나 경로 등을 바탕으로 트래픽을 정교하게 분산함.

## 🔒 Part 5. 암호화(Encryption) 및 SSL/TLS 기초

### 1. 암호화란?
* 수학적인 과정을 통해 어떤 정보를 읽을 수 없는 데이터로 변환하는 행위.
* **암호화 vs 해시(Hash):** 암호화는 복호화 키를 통해 '복원'이 가능하지만, 해시는 단방향 암호화이므로 복원이 불가능하다는 점이 가장 큰 차이점.

### 2. 주요 용어
* **평문 (Plaintext):** 암호화하기 전의 원본 데이터.
* **암호문 (Ciphertext):** 평문을 암호 키와 알고리즘을 사용해 알아볼 수 없게 변환한 데이터.
* **암호화 (Encryption):** 평문에 알고리즘과 키를 적용하여, 키를 소유한 주체가 아니면 알아볼 수 없는 암호문으로 만드는 과정.
* **복호화 (Decryption):** 암호문에 키와 복호화 알고리즘을 적용하여 다시 평문으로 되돌리는 과정.
* **키 (Key):** 평문을 암호화하거나 암호문을 평문으로 돌리기 위한 알고리즘의 핵심 가변 정보값 (자물쇠의 열쇠).
* **암호 알고리즘:** 암호화 및 복호화를 위해 사용되는 수학적 연산 규칙 (예: AES, DES, RSA 등).

### 3. 암호화 적용 상황에 따른 분류
* **저장된 데이터 보호 (Data at Rest):**
  * 데이터를 디스크나 DB에 저장할 때 암호화하고, 필요할 때 복호화해서 사용하는 방식.
  * 주로 물리적인 기기를 탈취당했을 때 데이터 유출을 막기 위해 사용 (키 파일 혹은 암호 이용).
* **전송 중 데이터 보호 (Data in Transit):**
  * 네트워크를 통해 데이터가 전송되는 과정에서 암호화를 적용하여 탈취를 막는 방식.
  * 주로 여러 시스템/기기 간에 통신 보안을 적용하기 위해 사용 (예: SSH, TLS, HTTPS).

### 4. 암호화 방식: 대칭키 vs 비대칭키
* **대칭키 암호화 (Symmetric Key):**
  * **단 하나의 똑같은 키**로 암호화와 복호화를 모두 수행하는 알고리즘.
  * *장점:* 연산이 가볍고 속도가 빠름.
  * *단점:* 나와 통신할 상대방에게 키를 안전하게 전달(공유)하는 방법에 대한 고민이 필요함.
* **비대칭키 암호화 (Asymmetric Key):**
  * **한 쌍의 키(공개키/비밀키)**를 활용하는 알고리즘. 하나의 키는 암호화만, 다른 하나는 복호화만 가능.
  * *장점:* 공개키는 누구에게나 배포해도 되므로 키 전달 및 관리가 비교적 쉬움.
  * *단점:* 대칭키에 비해 연산이 복잡하고 속도가 느림.
  * *원리:* 공개키(Public)로 암호화하면 비밀키(Private)로 복호화 가능. 반대로 비밀키로 암호화하면 공개키로 복호화 가능.

### 5. 암호화 서명 (Digital Signature)
* 키를 사용하여 특정 데이터가 진짜로 해당 생성자에 의해 만들어졌음을 보장(인증)하는 방법.
* 생성자가 자신의 **Private Key(비밀키)**를 사용하여 데이터에 서명을 생성하면, 누구나 해당 생성자의 **Public Key(공개키)**를 통해 그 서명이 유효한지 검증할 수 있음.

### 6. SSL / TLS
* 클라이언트와 서버 간에 데이터의 무결성과 기밀성을 보장할 수 있는 보안 프로토콜.
* 이 프로토콜이 적용된 HTTP가 바로 **HTTPS**임. (기존 HTTP는 평문으로 통신하여 중간 탈취에 취약함).
* 상호 간의 통신이 암호화되어 전달되므로, 중간에서 패킷을 가로채도 안전함.
* **통신 성립 3단계 (Handshake 과정):**
  1. **Cipher Suites 교환:** 양측이 지원하는 TLS 버전과 사용할 암호화 알고리즘 목록을 교환하여 통일.
  2. **인증서 검증:** 믿을 수 있는 인증기관(CA)에서 배포하는 인증서를 통해 서버의 실제 신원을 확인.
  3. **키 교환:** 대칭키와 비대칭키의 장점을 혼합하여, 앞으로의 통신에 사용할 빠르고 안전한 '대칭키(세션 키)'를 교환함.

## 🗄️ Part 6. 데이터베이스: RDBMS vs NoSQL

### 1. RDBMS (Relational Database Management System)
* **정의:** 데이터의 **관계(Relation)**에 집중하여, 행(Row)과 열(Column)로 구성된 2차원 테이블을 기반으로 정형화된 스키마 형식으로 데이터를 관리하는 시스템.
* **특징:** `SQL`을 사용하여 복잡한 쿼리와 데이터 간의 `JOIN` 연산이 가능함.
* **ACID 트랜잭션:** 데이터베이스의 상태 변화가 올바르게 이루어지도록 논리적인 작업 단위(트랜잭션)를 엄격하게 처리함.
  * **A (Atomicity, 원자성):** All or Nothing. 트랜잭션 내의 작업들은 전부 성공하거나 전부 실패해야 함. *(예: 내 계좌에서 돈 차감 + 어머니 계좌에 돈 추가가 하나의 세트로 처리됨)*
  * **C (Consistency, 일관성):** 트랜잭션 수행 전후에 데이터가 항상 올바른 상태를 유지해야 함. *(예: 송금 후에도 잔고가 음수가 되지 않아야 함)*
  * **I (Isolation, 독립성/고립성):** 동시에 실행되는 여러 트랜잭션은 서로 간섭하지 않고 독립적으로 수행되어야 함.
  * **D (Durability, 지속성):** 성공적으로 수행된 트랜잭션의 결과는 영구적으로 DB에 반영되어야 함.
* **AWS 주요 서비스:** `Amazon RDS`, `Amazon Aurora`, `Amazon Redshift`
* **주요 사용 사례:** 데이터의 무결성과 정확성이 매우 중요한 대부분 애플리케이션의 메인 DB.

### 2. NoSQL (Not Only SQL)
* **정의:** 정해진 스키마 없이 다양한 형식의 데이터를 유연하게 처리하는 데이터베이스 시스템.
* **특징:** 구조가 가볍고 확장성이 매우 뛰어남. 대부분 SQL 사용이 불가능하며 복잡한 쿼리보다는 간단하고 빠른 처리에 적합함.
* **주요 종류:**
  * **Key-Value Store:** Key-Value 쌍으로 데이터를 저장.
  * **Document Database:** JSON과 비슷한 일종의 문서 형식으로 데이터를 저장.
  * **Graph Database:** 데이터 간의 '연결'을 중심으로 데이터를 저장.
* **BASE 모델:** RDBMS의 엄격한 ACID에 비해 훨씬 느슨하고 분산 환경에 유연한 처리 모델.
  * **BA (Basically Available, 기본적 가용성):** 가용성을 중심으로 처리. 서버 장애가 발생하더라도 데이터는 다수 스토리지에 복제되어 있어 어떻게든 응답함.
  * **S (Soft-state, 소프트 상태):** DB의 상태는 느슨하며, 확정된 상태로 계속 유지되지 않고 자연스럽게 변화할 수 있음.
  * **E (Eventual Consistency, 결과적 일관성):** 쓰는 즉시 일관성이 확보되지는 않으나, 시간이 지나면 '언젠가(결과적으로)' 모든 노드의 데이터가 일관적인 상태로 수렴함.
* **AWS 주요 서비스:** `Amazon DynamoDB`, `Amazon MemoryDB (Redis)`, `Amazon ElastiCache (Redis, Memcached)`
* **주요 사용 사례:** 빠른 응답이 필요한 캐시(Cache), 단순하고 방대한 데이터 저장, 추천 로직 등 각 DB 구조에 맞는 서비스.
