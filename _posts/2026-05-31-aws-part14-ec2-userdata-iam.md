EC2를 처음 띄울 때 자동으로 설정을 완료하거나, 실행 중인 인스턴스가 자기 정보를 확인하거나, 다른 AWS 서비스에 안전하게 접근하는 세 가지 기능을 함께 정리합니다.

## EC2 User Data (유저 데이터)

> **정의:** EC2 인스턴스가 **최초로 실행될 때** 자동으로 지정한 스크립트를 실행하게 해주는 기능

> **비유:** 새 직원이 첫 출근하면 자동으로 신입 교육 과정을 밟는 것처럼,  
> 새 인스턴스가 처음 켜지면 지정된 스크립트가 자동으로 실행됩니다.

### 왜 필요한가?

EC2를 새로 만들 때마다 수작업으로 패키지 설치하고 설정 파일을 수정하는 것은 번거롭고 실수가 생깁니다.  
User Data를 활용하면 **인프라를 코드로 관리(IaC)** 하는 첫걸음을 뗄 수 있습니다.

```bash
#!/bin/bash
# 최초 실행 시 자동으로 Apache 웹서버 설치 및 시작
yum update -y
yum install -y httpd
systemctl start httpd
systemctl enable httpd
echo "<h1>Hello from EC2!</h1>" > /var/www/html/index.html
```

### 주요 특성

| 특성 | 내용 |
|---|---|
| **실행 시점** | 인스턴스 **최초 시작 시** 1회 실행 (기본값) |
| **지원 형식** | Shell Script (`#!/bin/bash`) 또는 `cloud-init` 지시문 |
| **실행 권한** | root 권한으로 실행됨 |

### 주요 활용 사례

```
✅ 보안 설정 (패치 업데이트, 방화벽 설정)
✅ 패키지 다운로드 및 설치 (Apache, Nginx, Java 등)
✅ 애플리케이션 설치 및 서비스 시작
✅ 외부 저장소(S3 등)에서 코드 받아서 실행
```

## EC2 Instance Metadata (메타데이터)

> **정의:** 실행 중인 인스턴스를 구성하거나 관리하는 데 사용되는 **해당 인스턴스만의 고유 정보**

> **비유:** 인스턴스가 자기 자신의 주민등록증을 조회하는 것과 같습니다.  
> 인스턴스 **내부에서** 특정 IP(`169.254.169.254`)로 HTTP 요청을 보내 무료로 조회합니다.  
> 이 IP는 링크-로컬 주소로, 인스턴스 외부에서는 접근 불가합니다.

### 조회 가능한 정보

| 정보 | 설명 |
|---|---|
| AMI ID | 이 인스턴스를 만든 AMI |
| IPv4 / IPv6 주소 | Private/Public IP |
| 호스트 이름 | 인스턴스의 DNS 이름 |
| 보안 그룹 | 연결된 보안 그룹 목록 |
| IAM 역할 | 부여된 IAM 역할 및 임시 자격증명 |
| 인스턴스 타입 | 현재 인스턴스의 유형과 크기 |

---

## IMDS 버전 비교 (v1 vs v2)

IMDS(Instance Metadata Service)는 메타데이터를 제공하는 서비스로, 보안 수준이 다른 두 버전이 있습니다.

### IMDS v1 — 단순 요청/응답 방식

```bash
# 별도 인증 없이 바로 조회 가능
curl http://169.254.169.254/latest/meta-data/instance-id
```

- 간편하지만 **SSRF(서버 사이드 요청 위조) 공격에 취약**

### IMDS v2 — 세션 기반 방식

> **비유:** v1이 열쇠 없는 보관함이라면, v2는 먼저 임시 열쇠를 받아야 열 수 있는 보관함입니다.

```bash
# 1단계: 임시 토큰 발급
TOKEN=$(curl -X PUT "http://169.254.169.254/latest/api/token" \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")

# 2단계: 토큰을 헤더에 넣어 메타데이터 조회
curl -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/instance-id
```

| 항목 | v1 | v2 |
|---|---|---|
| **인증 방식** | 없음 (바로 조회) | 세션 토큰 필요 |
| **SSRF 공격 방어** | 취약 | 방어 가능 |
| **토큰 유효기간** | 해당 없음 | 1초 ~ 최대 6시간 |

> **💡 AWS 권장:** 새로 만드는 인스턴스는 기본적으로 **IMDS v2만 사용**하도록 설정하는 것이 보안 모범 사례입니다.

## EC2 IAM 역할 — 키 없이 AWS 서비스 접근하기

EC2 위에서 돌아가는 애플리케이션이 S3, DynamoDB 같은 다른 AWS 서비스에 접근하려면 반드시 **권한**이 있어야 합니다.

### 방식 A: IAM 자격 증명 직접 등록 — 비권장

```bash
# EC2 인스턴스 내부에서 실행
aws configure
# AWS Access Key ID: AKIAXXXXXXXXXXXXXXXX
# AWS Secret Access Key: xxxxxxxx...
```

**치명적인 단점:**

```
EC2 100대가 돌아가는 상황에서 보안 이슈로 키를 교체해야 한다면?
→ 100대에 일일이 SSH 접속
→ 100대에서 새 키 값 입력
→ 운영 부담이 매우 크고, 실수할 가능성도 높습니다.
```

---

### 방식 B: IAM 역할(Role) 부여 — AWS 권장 모범 사례

> **비유:** IAM 역할은 사람(사용자)뿐만 아니라 AWS 서비스(EC2, Lambda 등)가 임시로 쓸 수 있는 **'모자'나 '사원증'**과 같습니다.

```
IAM 역할 → 인스턴스 프로파일(Instance Profile) → EC2 연동
```

역할이 부여된 인스턴스 내부에서는 키 없이 AWS CLI와 SDK를 바로 사용할 수 있습니다.

```bash
# EC2 내부에서 aws configure 없이 바로 사용 가능
aws s3 ls
aws iam list-users
```

**장점:**

| 장점 | 내용 |
|---|---|
| **쉬운 권한 관리** | IAM 콘솔에서 역할의 정책 하나만 수정하면 연결된 모든 EC2에 즉시 반영 |
| **자동 키 교체(Rotation)** | AWS가 내부적으로 임시 자격 증명을 생성하고 주기적으로 자동 교체 |
| **키 유출 위험 최소화** | 하드코딩된 키가 없으므로 인스턴스가 탈취돼도 영구 키 유출 없음 |

**내부 동작 원리:**

```
EC2 내부 앱이 AWS API 호출 시도
    ↓
AWS SDK가 자동으로 IMDS(메타데이터 서비스) 조회
    ↓
인스턴스에 연결된 IAM 역할의 임시 자격 증명 획득
    ↓
임시 자격 증명으로 S3, IAM 등 API 호출 성공
```

## IAM 역할이 부여될 수 있는 대상

| 대상 | 예시 |
|---|---|
| **EC2 인스턴스** | 인스턴스에서 실행 중인 앱이 S3, DynamoDB에 접근 |
| **Lambda 함수** | 함수가 S3 파일을 읽고 처리 |
| **ECS 태스크** | 컨테이너가 Secrets Manager에서 비밀 값 조회 |
| **다른 AWS 계정** | 크로스 계정 접근을 위한 역할 위임 |

---

## 두 방식 비교

| 항목 | IAM 자격 증명 직접 등록 | IAM 역할 부여 |
|---|---|---|
| **키 파일 존재** | O (파일에 저장) | X (임시 자격 증명만 사용) |
| **키 교체** | 수동, 모든 인스턴스에 직접 변경 | 자동 (AWS가 주기적으로 교체) |
| **권한 수정** | 각 인스턴스 개별 수정 | 역할 하나만 수정 → 전체 반영 |
| **보안성** | 낮음 (키 유출 위험) | 높음 (임시 키, 자동 만료) |
| **AWS 권장 여부** | ❌ 비권장 | ✅ 권장 모범 사례 |

## User Data vs Metadata 비교

| 항목 | User Data | Metadata |
|---|---|---|
| **방향** | 외부 → 인스턴스 (스크립트 주입) | 인스턴스 → 자기 자신 (정보 조회) |
| **시점** | 인스턴스 시작 시 | 언제든 실행 중에 조회 가능 |
| **주요 용도** | 초기 환경 설정 자동화 | 자기 IP, IAM 역할 등 동적 정보 획득 |
