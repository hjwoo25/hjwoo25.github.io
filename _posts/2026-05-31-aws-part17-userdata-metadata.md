EC2를 처음 띄울 때 자동으로 설정을 완료하거나, 실행 중인 인스턴스가 자기 자신의 정보를 확인해야 할 때 사용하는 두 가지 기능을 정리합니다.

---

## EC2 User Data (유저 데이터)

> **정의:** EC2 인스턴스가 **최초로 실행될 때** 자동으로 지정한 스크립트를 실행하게 해주는 기능

> **비유:** 새 직원이 첫 출근하면 자동으로 신입 교육 과정을 밟는 것처럼,  
> 새 인스턴스가 처음 켜지면 지정된 스크립트가 자동으로 실행됩니다.

### 왜 필요한가?

EC2를 새로 만들 때마다 수작업으로 패키지 설치하고 설정 파일을 수정하는 것은 번거롭고 실수가 생깁니다.  
User Data를 활용하면 **인프라를 코드로 관리(IaC)** 하는 첫걸음을 뗄 수 있습니다.

```bash
#!/bin/bash
# 최초 실행 시 자동으로 Apache 웹서버 설치 및 시작
yum update -y
yum install -y httpd
systemctl start httpd
systemctl enable httpd
echo "<h1>Hello from EC2!</h1>" > /var/www/html/index.html
```

### 주요 특성

| 특성 | 내용 |
|---|---|
| **실행 시점** | 인스턴스 **최초 시작 시** 1회 실행 (기본값) |
| **반복 실행** | 설정 변경 시 재부팅마다 실행되도록 할 수도 있음 |
| **지원 형식** | Shell Script (`#!/bin/bash`) 또는 `cloud-init` 지시문 |
| **실행 권한** | root 권한으로 실행됨 |

### 주요 활용 사례

```
✅ 보안 설정 (패치 업데이트, 방화벽 설정)
✅ 패키지 다운로드 및 설치 (Apache, Nginx, Java 등)
✅ 애플리케이션 설치 및 서비스 시작
✅ 설정 파일 작성 및 환경 변수 설정
✅ 외부 저장소(S3 등)에서 코드 받아서 실행
```

## 실습: EC2로 웹서버 만들기

앞서 배운 내용을 종합하여 실제 웹서버를 구축하고 AMI로 복제하는 시나리오입니다.

```
1. EC2 프로비전
   - 인스턴스 타입: t2.micro
   - AMI: Amazon Linux 3

2. 보안 그룹 설정
   - 80 포트 (HTTP): 전체 허용
   - 22 포트 (SSH): 내 IP만 허용

3. User Data로 Apache 자동 설치
   #!/bin/bash
   yum install -y httpd
   systemctl start httpd
   systemctl enable httpd

4. 웹 브라우저에서 퍼블릭 IP로 접속 확인

5. 나만의 AMI 생성
   → 기존 인스턴스 종료
   → 생성한 AMI로 동일 환경의 새 인스턴스 시작 ✅
```

> 한 번 세팅된 서버 환경을 AMI로 저장해두면, 동일한 환경을 필요할 때마다 즉시 복제할 수 있습니다.

## EC2 Instance Metadata (메타데이터)

> **정의:** 실행 중인 인스턴스를 구성하거나 관리하는 데 사용되는 **해당 인스턴스만의 고유 정보**

> **비유:** 인스턴스가 자기 자신의 주민등록증을 조회하는 것과 같습니다.  
> 외부에서 물어보는 게 아니라, **인스턴스 내부에서 자기 정보를 꺼내 보는** 방식입니다.

### 조회 가능한 정보

| 정보 | 설명 |
|---|---|
| AMI ID | 이 인스턴스를 만든 AMI |
| IPv4 / IPv6 주소 | Private/Public IP |
| 호스트 이름 | 인스턴스의 DNS 이름 |
| 보안 그룹 | 연결된 보안 그룹 목록 |
| IAM 역할 | 부여된 IAM 역할 및 임시 자격증명 |
| 인스턴스 타입 | 현재 인스턴스의 유형과 크기 |

### 조회 방법

인스턴스 **내부**에서 특정 IP(`169.254.169.254`)로 HTTP 요청을 보내 무료로 조회할 수 있습니다.  
이 IP는 링크-로컬 주소로, **인스턴스 외부에서는 접근 불가**합니다.

> Tag 정보는 기본적으로 조회되지 않으며, 별도로 활성화해야 합니다.

## IMDS 버전 비교 (v1 vs v2)

IMDS(Instance Metadata Service)는 메타데이터를 제공하는 서비스로, 보안 수준이 다른 두 버전이 있습니다.

### IMDS v1 — 단순 요청/응답 방식

```bash
# 별도 인증 없이 바로 조회 가능
curl http://169.254.169.254/latest/meta-data/instance-id
curl http://169.254.169.254/latest/meta-data/public-ipv4
```

- 보안 인증 없이 HTTP 요청만으로 즉시 조회
- 간편하지만 **SSRF(서버 사이드 요청 위조) 공격에 취약**

---

### IMDS v2 — 세션 기반 방식

> **비유:** v1이 열쇠 없는 보관함이라면, v2는 먼저 임시 열쇠를 받아야 열 수 있는 보관함입니다.

```bash
# 1단계: 임시 토큰 발급 (유효시간 최대 6시간, 최소 1초)
TOKEN=$(curl -X PUT "http://169.254.169.254/latest/api/token" \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")

# 2단계: 토큰을 헤더에 넣어 메타데이터 조회
curl -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/instance-id
```

**v2의 보안 강화 포인트:**

| 항목 | v1 | v2 |
|---|---|---|
| **인증 방식** | 없음 (바로 조회) | 세션 토큰 필요 |
| **SSRF 공격 방어** | 취약 | 방어 가능 |
| **토큰 유효기간** | 해당 없음 | 1초 ~ 최대 6시간 |
| **v2 강제 적용** | 불가 | IAM 정책으로 v2만 허용 가능 |

```
[v2 강제 적용 정책 예시]
인스턴스에 IAM 정책 적용:
"ec2:MetadataHttpTokens" = "required"
→ 토큰 없이 오는 v1 방식 요청은 전부 거부 ✅
```

> **💡 AWS 권장:** 새로 만드는 인스턴스는 기본적으로 **IMDS v2만 사용**하도록 설정하는 것이 보안 모범 사례입니다.

## User Data vs Metadata 비교

| 항목 | User Data | Metadata |
|---|---|---|
| **방향** | 외부 → 인스턴스 (스크립트 주입) | 인스턴스 → 자기 자신 (정보 조회) |
| **시점** | 인스턴스 시작 시 | 언제든 실행 중에 조회 가능 |
| **주요 용도** | 초기 환경 설정 자동화 | 자기 IP, IAM 역할 등 동적 정보 획득 |
| **비용** | 무료 | 무료 |
