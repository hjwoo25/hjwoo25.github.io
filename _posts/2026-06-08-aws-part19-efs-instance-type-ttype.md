## Amazon EFS (Elastic File System)

> **정의:** 여러 대의 EC2 인스턴스가 동시에 접근하여 파일을 읽고 쓸 수 있는 네트워크 기반 공유 스토리지 서비스 (NFSv4)

> **비유:** 공항 공유 라운지 짐 보관소입니다.  
> EBS가 특정 기체에만 붙은 전용 짐 보관함이라면, EFS는 어느 기체 승무원이든 동시에 드나들 수 있는 공용 보관소입니다.  
> 짐이 늘면 자동으로 공간이 넓어지고, 짐을 빼면 줄어듭니다. 공간을 미리 예약할 필요가 없습니다.

### EBS vs EFS 핵심 차이

| 항목 | EBS | EFS |
|---|---|---|
| 접근 방식 | EC2 **1대**에만 연결 | EC2 **수천 대** 동시 접근 |
| 연결 범위 | 동일 AZ 내 | 여러 AZ에 걸쳐 접근 가능 |
| 용량 | 미리 지정 (최대 64TB) | 자동 확장 (페타바이트까지) |
| 과금 | 할당 용량 기준 | **사용한 용량**만큼만 |
| OS | Linux / Windows | **Linux 전용** |

### 주요 특징

- **자동 확장:** 파일 추가 시 용량이 자동으로 늘고, 삭제하면 줄어듭니다. 용량을 미리 지정하거나 관리할 필요가 없습니다.
- **고가용성:** 데이터가 여러 가용 영역(AZ)에 분산 저장되어 단일 AZ 장애에도 데이터가 안전합니다.
- **제한 사항:** Linux에서만 사용 가능(Windows 불가), 기본적으로 VPC 내부망(Private)에서만 접근 가능합니다. 온프레미스에서 접근하려면 VPN 또는 Direct Connect가 필요합니다.

## EFS 유형 및 모드

### 타입 (Type)

| 타입 | 설명 | 특징 |
|---|---|---|
| **Regional** | 리전 내 여러 AZ 활용 | 높은 가용성, 기본 권장 |
| **One-Zone** | 단일 AZ만 사용 | 저렴하지만 가용성 낮음 |

### 퍼포먼스 모드 (Performance Mode)

| 모드 | 설명 | 적합한 경우 |
|---|---|---|
| **General Purpose** | 일반적인 목적 | 웹서버, CMS, 홈 디렉토리 |
| **Max I/O** | 극단적으로 높은 I/O | 빅데이터 분석, 미디어 처리 |

### 처리량 모드 (Throughput Mode)

| 모드 | 설명 | 특징 |
|---|---|---|
| **Elastic** ⭐ | 사용량에 따라 자동 조절 | AWS 권장, 예측 불가 워크로드에 적합 |
| **Bursting** | 평소에 크레딧 적립, 피크 시 소모 | T-타입 인스턴스와 유사한 원리 |
| **Provisioned** | 사용자가 처리량을 고정 지정 | 고정된 높은 처리량이 필요한 경우 |

## EC2 인스턴스 타입 변경

클라우드의 핵심 장점 중 하나는 처음 생성한 서버의 사양이 부족하거나 과할 때 언제든 **인스턴스 크기나 패밀리를 변경**할 수 있다는 점입니다.

> **비유:** 운항 중인 기체를 더 크거나 작은 기종으로 교체하는 것입니다.  
> 반드시 착륙(Stop)해서 정비 상태로 만든 뒤에만 기종 교체가 가능합니다.  
> 기체가 바뀌어도 노선(인스턴스 ID)과 내선번호(Private IP)는 그대로입니다.

### 변경 시 주의사항

| 항목 | 내용 |
|---|---|
| **사전 조건** | 반드시 인스턴스 **Stop 상태**에서만 변경 가능 |
| **호환성** | ARM/32bit 등 아키텍처·가상화 타입이 다르면 변경 불가 |
| **유지되는 것** | 인스턴스 ID, **Private IP** |
| **변경되는 것** | **Public IP** (Elastic IP 연결 시 예외) |
| **Spot 인스턴스** | 타입 변경 불가 |

### 스토리지 종류에 따른 변경 방법

#### EBS 기반 인스턴스 — 비교적 간단

```
아키텍처 호환 ✅
  → 인스턴스 Stop → 타입 변경 → Start
  → 기존 EBS가 그대로 새 인스턴스에 연결됨

아키텍처 호환 ❌
  방법 1: EBS Detach → 새 인스턴스 생성 → EBS Attach
  방법 2: 스냅샷 → 새 AMI → 새 인스턴스 생성
```

> **비유:** 기체만 바꾸고 짐 보관함(EBS)은 그대로 새 기체에 이전합니다.  
> 기체 구조가 달라서 짐 보관함 규격이 안 맞으면, 짐을 빼서 따로 보내고(Detach) 새 기체에 다시 싣거나(Attach), 짐 목록 사진(스냅샷)을 찍어서 새 기체에 맞게 다시 꾸립니다.

#### 인스턴스 스토어 기반 — 반드시 백업 먼저

```
인스턴스 스토어 = 기체 내부 짐칸
  → 기체를 교체하면 내부 짐칸은 사라짐 ❌

방법: 먼저 데이터 외부 백업 → 새 인스턴스 프로비저닝
```

> **비유:** 기체 내부 짐칸(인스턴스 스토어)은 기체가 바뀌면 내용물이 모두 사라집니다.  
> 반드시 짐을 외부 보관소(S3 등)로 옮긴 뒤에 새 기체를 준비해야 합니다.

## EC2 T-타입 인스턴스 (Burstable Performance)

> **정의:** CPU 자원을 100% 고정 할당하지 않고, **CPU 크레딧(Credit)** 이라는 개념을 활용하는 가성비 서버 (T2, T3, T4g 등)

> **비유:** 연료 크레딧 시스템을 갖춘 경제형 기체입니다.  
> 평소 순항 속도(베이스라인)로만 날면 연료 크레딧이 쌓이고,  
> 이착륙처럼 순간 풀 스로틀이 필요할 때 모아둔 크레딧을 소모해 최대 출력을 냅니다.

### 크레딧 작동 원리

**베이스라인 (Baseline):** 인스턴스 크기별로 정해진 기준 CPU 사용률

| 인스턴스 | 베이스라인 | 최대 vCPU |
|---|---|---|
| t3.nano | 5% | 2 |
| t3.micro | 10% | 2 |
| t3.small | 20% | 2 |
| t3.medium | 20% | 2 |

```
CPU 사용 < 베이스라인  →  크레딧 적립 (통장에 돈 쌓임)
CPU 사용 > 베이스라인  →  크레딧 소모하며 버스트 (최대 100% 출력)
```

> **주의:** 크레딧은 최대 **24시간 치**까지만 쌓이고, 초과분은 버려집니다.

### Standard vs Unlimited 모드

> **비유:** 크레딧이 바닥났을 때 어떻게 할 것인지의 차이입니다.

| 항목 | Standard | Unlimited |
|---|---|---|
| **T2 기본값** | ✅ Standard | — |
| **T3 기본값** | — | ✅ Unlimited |
| **크레딧 소진 시** | CPU를 베이스라인으로 **강제 제한** | 계속 버스트 가능 |
| **추가 요금** | 없음 | **24시간 내 미상환 시 과금** |
| **위험** | 서비스 응답 불가 (500 에러, 먹통) | 요금 폭탄 |

**Standard 모드 위험 시나리오:**
```
크레딧 잔량 0 도달
  → CPU가 베이스라인(예: 10%)으로 강제 제한
  → 웹서버 500 에러, 애플리케이션 먹통
  → 사용자 서비스 장애 발생
```

**Unlimited 모드 위험 시나리오:**
```
크레딧 잔량 0 도달
  → 미래 크레딧 선차입(마이너스 통장)
  → 24시간 내 상환 못 하면 추가 요금 발생
  → 24/7 CPU를 빡세게 쓰면 요금 폭탄
```

> **T2 시작 시 Launch Credit:** 처음 생성 직후 크레딧이 없어 부팅 단계부터 버스트가 필요할 수 있으므로, AWS가 Launch Credit을 소량 무료로 지급합니다.

### T-타입 적합한 vs 부적합한 워크로드

| 적합 ✅ | 부적합 ❌ |
|---|---|
| 개발·테스트 서버 | 24/7 고부하 라이브 서비스 |
| 가벼운 웹서버 | CPU 집약적 데이터 처리 |
| 트래픽이 가끔씩 튀는 서비스 | 게임 서버, ML 학습 |
| 소규모 내부 툴 | 지속적인 스트리밍 서비스 |

### 모니터링 필수 지표

CloudWatch에서 반드시 확인해야 할 지표:

```
CPUCreditBalance    → 크레딧 잔량 (0에 가까워지면 위험)
CPUCreditUsage      → 시간당 소모 크레딧
CPUSurplusCredits   → Unlimited 모드에서 선차입한 크레딧 양
```

> **결론:** T-타입은 평소엔 순항 속도로 연료를 아끼다가 필요할 때만 풀 스로틀을 내는 경제형 기체입니다. 하지만 24시간 내내 풀 스로틀을 요구하는 노선에 투입하면, Standard는 기체가 멈추고 Unlimited는 연료비 폭탄을 맞습니다. CloudWatch로 크레딧 잔량을 꼭 모니터링하세요.
