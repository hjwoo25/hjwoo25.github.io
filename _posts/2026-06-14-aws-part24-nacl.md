보안 그룹이 서버의 '개인 경호원'이라면, NACL은 서브넷 마을 전체를 지키는 '거대한 성벽과 성문'입니다. Stateless 동작 원리, 규칙 번호 우선순위, 임시 포트 개방, 기본 NACL vs 커스텀 NACL까지 빠짐없이 정리합니다.

---

## 네트워크 ACL(NACL)의 기본 개념

> **비유:**
> - **NACL (성문 수비대):** "이 마을(서브넷)에는 `112.12.35.4`라는 강도(해커)는 절대 못 들어와!" 하고 마을 입구에서부터 쫓아냅니다.
> - **보안 그룹 (집 앞 경호원):** 마을에 들어온 사람들 중, 내 집(인스턴스) 문을 두드리는 사람만 명단과 대조해 문을 열어줍니다.

네트워크 ACL(Network Access Control List)은 **1개 이상의 서브넷 내부와 외부를 오가는 트래픽을 제어하는** 방화벽 역할을 하는 VPC의 선택적 보안 계층입니다.

### 핵심 특징

| 항목 | 내용 |
|---|---|
| **방어 단위** | **서브넷 단위** (보안 그룹은 인스턴스 단위) |
| **다중 연동** | 하나의 NACL을 여러 서브넷에 동시에 연결 가능 (1:N) |
| **Deny 규칙** | **가능** — 특정 포트나 IP를 직접 거부(Deny)할 수 있음 |
| **주 용도** | 외부 공격을 받는 상황에서 해커의 IP를 원천 차단 |

---

## Stateless (상태를 기억하지 못함) — 핵심 주의

> **비유:** 기억상실증에 걸린 경비원입니다.  
> 들어갈 때 신분증을 보여주고(Inbound 규칙 통과) 들어갔더라도,  
> 나올 때 "너 누구야? 나가는 허가증(Outbound 규칙) 있어?" 라며 또 막아 세웁니다.  
> 나갈 때를 대비해 나가는 통로(임시 포트)도 미리 허가해 두어야만 무사히 나갈 수 있습니다.

보안 그룹이 한 번 들어온 사람을 기억하는 **Stateful** 방식이었다면, NACL은 아주 매정하고 기억력이 없는 **Stateless** 방식입니다.

- 들어오는 트래픽(Inbound)과 나가는 트래픽(Outbound)을 **전혀 구분하지 않고**, 각각 따로따로 규칙을 검사합니다.
- **임시 포트(Ephemeral Port) 개방 필수:** 클라이언트가 80번 포트(웹)로 요청을 보낼 때, 들어오는 문(Inbound 80)만 열어두면 안 됩니다. 서버가 응답을 돌려보낼 때는 클라이언트의 임시 포트로 나가야 하므로, **나가는 문(Outbound)에 임시 포트 범위를 반드시 열어주어야** 정상적인 통신이 가능합니다.

## NACL 규칙(Rule) 작성법

### 규칙 구성 항목

| 항목 | 설명 |
|---|---|
| **유형 & 프로토콜** | SSH(22), DNS(53), UDP, TCP, ALL 등 |
| **포트 범위** | 허용/거부할 포트 |
| **소스** | 대상이 되는 IP 주소 대역 (CIDR) |
| **허용/거부** | Allow 또는 Deny |

### 규칙 번호의 평가 순서 (매우 중요)

각 규칙에는 고유 번호가 부여되며, **번호가 낮을수록 먼저 평가**됩니다.

- 번호를 매길 때는 나중에 중간에 새 규칙을 끼워 넣기 쉽도록 **100 단위로 증가**시키는 것을 AWS가 권장합니다.
- 목록 맨 마지막에는 항상 **`*` 번호가 붙은 암묵적인 규칙**이 존재하며, 위에서 일치하는 규칙이 없으면 **나머지는 전부 거부(Deny)**합니다.

### 규칙 순서 예시 1

| 번호 | 소스 | 포트 | 동작 |
|---|---|---|---|
| 100 | `112.12.35.4` | ALL | **Deny** |
| 200 | `0.0.0.0/0` | ALL | **Allow** |
| * | — | — | Deny |

**결과:** 100번이 먼저 평가되므로 **해커 IP(`112.12.35.4`)는 차단**되고, 나머지 모든 IP는 200번 규칙에 의해 통과됩니다.

### 규칙 순서 예시 2

| 번호 | 소스 | 포트 | 동작 |
|---|---|---|---|
| 50 | `112.12.35.4` | 3306 | **Allow** |
| 100 | `112.12.35.4` | 80 | **Deny** |
| 200 | `0.0.0.0/0` | 80 | **Allow** |
| * | — | — | Deny |

**결과:** 해커 IP라도 **3306 포트(DB)로 들어오는 것은 허용**되지만, **웹(80 포트)으로 들어오는 것은 차단**됩니다. 번호가 낮은 규칙이 무조건 이깁니다!

## 실무를 위한 NACL 주요 고려사항

### 1) 운영체제별 임시 포트(Ephemeral Port) 허용 범위

Stateless 방화벽인 NACL을 원활하게 쓰려면 **Outbound 규칙에 다음 포트들을 열어두어야** 합니다.

| 운영체제 | 임시 포트 범위 |
|---|---|
| **Linux** | 32768 ~ 61000 |
| **Windows XP** | 1025 ~ 5000 |
| **Windows Vista 이상** | 49152 ~ 65535 |

### 2) 서브넷 '내부' 트래픽에는 미적용

- NACL은 서브넷에서 **나가거나 들어오는 트래픽에만** 적용됩니다.
- 같은 서브넷(마을) 안에서 A 집과 B 집이 통신하는 **내부 트래픽에는 NACL이 아예 개입하지 않습니다.**
- 멀티 티어 아키텍처(여러 서브넷을 거치는 구조)라면 트래픽이 서브넷을 넘어갈 때마다 NACL을 통과해야 하므로 **설계 시 많은 고민이 필요**합니다.

### 3) AWS 권장사항

가능한 관리가 편한 **보안 그룹으로 먼저 방화벽을 처리**하고, 꼭 필요한 특정 IP 차단 등에만 **NACL을 보조로 활용**하는 것이 좋습니다.

### 4) 기본 NACL vs 커스텀 NACL

| 항목 | 기본 NACL (Default) | 커스텀 NACL (Custom) |
|---|---|---|
| **생성** | VPC 생성 시 자동으로 1개 제공 | 사용자가 직접 생성 |
| **초기 설정** | 모든 트래픽 **Allow (허용)** | 모든 트래픽 **Deny (거부)** |
| **사용법** | 그대로 사용 가능 | 직접 하나하나 열어주어야 함 |

### 5) NACL과 서브넷의 연동 규칙

```
NACL A ──┬── 서브넷 B
         ├── 서브넷 C    ← 하나의 NACL → 여러 서브넷 (1:N 가능)
         └── 서브넷 D

서브넷 A ──── NACL A      ← 하나의 서브넷 → 오직 하나의 NACL만
         ✖── NACL B      ← 다른 NACL로 변경하면 기존 연결 끊김
```

- 하나의 NACL은 **여러 서브넷을 한꺼번에 관리**할 수 있습니다.
- 하지만 하나의 서브넷은 **오직 하나의 NACL에만 연동** 가능합니다.
- 서브넷 A가 'NACL A'에 연결되어 있는데, 강제로 'NACL B'에 연결하면 **기존 'NACL A'와의 연결은 끊어집니다.**

## 보안 그룹 vs NACL 최종 비교

| 항목 | 보안 그룹 | NACL |
|---|---|---|
| **방어 대상** | 인스턴스 (ENI) 단위 | 서브넷 단위 |
| **상태** | Stateful (기억함) | Stateless (기억 못함) |
| **규칙 방식** | Allow만 가능 | Allow + Deny 가능 |
| **규칙 평가** | 모든 규칙 종합 평가 | 번호 낮은 순서대로 평가 |
| **적용 범위** | 보안 그룹이 연결된 인스턴스만 | 서브넷의 모든 트래픽 |
| **임시 포트** | 자동 허용 (Stateful) | 직접 열어야 함 |
